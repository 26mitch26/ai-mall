# 四、自动化测试 Agent 专项（从"能跑的脚本"到"可被 Agent 编排的测试系统"）

> **2026-10-07核验：** 本文保留早期工程/选型阶段的记录，未重测的数值不是当前结果。当前任务评测、模型入口、分块与登录状态以 [产品评测报告](../eval/product-evaluation-report.md)、[最终实验报告](../实验报告-最终版.md) 和 [Chunk策略审查](product/chunk-strategy-review.md) 为准。旧子块实验不否定完整父段恢复；历史来源命中与测试通过不能当作真实解决率。


> 这篇讲一个自动化测试 Agent 的完整设计：期望值治理、断言分层、噪音分类、
> 缺陷回流、LLM judge 质量评测、MCP 接入。适合后端/测试/平台岗位面试。

---

## 1. 定位与四层能力

| 模块名 | 层 | 测什么 | 判定依据 |
|---|---|---|---|
| `mall-portal` / `mall-admin` | 契约层 | OpenAPI 发现 → 用例生成 → 真实 HTTP | **OpenAPI 声明是唯一 oracle** |
| `agent-customer-scenarios` | 会话层 | 11 条关键路径：意图、工具取数、来源、拒答、401 边界 | 关键词断言 + 来源数 |
| `agent-customer-quality` | 质量评测层 | 149 条 gold 集（类别轮询取样） | 来源命中/拒答/注入阻断 + 可选 LLM judge |
| 全部 | 洞察层 | 失败回流为"已知缺陷"，标注第 N 次复现 | 语义断言失败与 5xx 算高价值信号，连接噪音不算 |

**为什么要分层**：契约绿 ≠ 功能可用。真实案例（实验记录 Failure Case 09）：
用户问"我买了哪些东西"，契约 14 条全绿，但会话链路答不出来——
契约层只验证"接口存在、参数与状态码行为"，不覆盖"口语问法 → 意图 → 工具取数"。

## 2. 期望值治理（本项目最核心的设计）

**问题**：测试最容易错的地方不是"跑不起来"，而是**期望值从哪来**。
人工写期望值会带上主观臆测；让 LLM 猜状态码会"看起来合理地编造"。

**我的做法：把 OpenAPI 声明当唯一 oracle。**

- 正向用例：锚定文档声明的**最小 2xx**；文档没声明任何成功码 → **用例作废**（不猜）；
- 负向用例：文档声明了该码 → 精确断言；未声明 → 降级为"以 4xx 拒绝"的弱断言
  （"返回 400 还是 422"属实现细节，不是契约承诺）；
- AI 生成的用例统一过 `TestCaseContractGuard`：方法/路径/参数名/状态码四类幻觉逐一拦截，
  未声明的 2xx/5xx 直接丢弃。

**为什么这条最值得讲**：它把"测试的可靠性"从"写测试的人有多认真"变成了"契约文档有多准"，
并且给出了契约不严谨时的**明确降级路径**，而不是让整套测试变得脆不可用。

## 3. 用例生成：规则与 LLM 各管一段

- **规则路径**（默认，AI 关闭）：成功 / 缺必填 / 非法值 / 数值负数边界 4 类，快且完全可复现；
- **LLM 路径**（`TEST_AGENT_AI_ENABLED=true`）：探索性用例 + 正常/异常/边界三件套
  （空串、超长、5 种注入串、数值 -1/0/Long.MAX_VALUE、非法布尔…），全部过契约守卫；
- **AI 默认关闭**是刻意的：现场演示要可复现，而 LLM 用例有三重不可复现性
  （temperature 0.3、管道分隔文本协议、`UUID` 用例 id）。

⚠️ 副作用要说清：AI 关闭时报告里的"场景覆盖"维度会退化（"正常/异常/边界"分类依赖用例名前缀）。

## 4. 断言分层

| 断言 | 实现 | 抓什么 |
|---|---|---|
| 状态码分档 | strict 精确相等 / weak 要求 4xx | 契约违背 |
| JSON Schema | 手写轻量子集校验（不引外部库，因 OpenAPI 响应多用 `$ref`，脱离文档上下文会误报） | 结构违规 |
| 业务码吞错 | 根节点有数字 `code` 且 HTTP 2xx 时 `code` 必须 200 | "HTTP 200 + {code:500}"这类假成功 |
| 分页不变式 | `total >= list.size()` | 分页元数据与实际条数矛盾 |
| 响应时延 | 阈值断言（默认 5000ms） | 性能回归 |
| Schema `$ref` 处理 | 遇 `$ref` 直接跳过而非误判 | —— |

⚠️ 已知局限：`$ref` 直接跳过的代价是**这条断言在真实 Spring 响应里大面积静默失效**
（"宁漏报不误报"的有意识取舍）。

## 5. 噪音分类：让红灯有意义

不是所有失败都是产品缺陷。`FailureClassifier` 的白名单只认三条语义断言
（业务码 / Schema / 分页不变式）+ 5xx 判为高价值信号；**连接类失败判为噪音不沉淀**；
纯状态码偏差信号不足也不沉淀。

会话/评测类结果走另一条规则（`classifyConversational`）：断言名是动态拼的
（"回答包含[退货]"），不可能进白名单，因此**除环境噪音外一律沉淀**，
并按 `POST /chat#<用例ID>` 聚合（按端点聚合会互相覆盖失败原因）。

## 6. 环境归因与被测鉴权（两处"让红灯可信"的改造）

1. **开跑前探针**：先打 `/actuator/health`，把可达性与耗时写进报告，报告头部显式标注，
   前端弹红/绿提示。实测被测服务没起时 14 条全红，但报告自证"环境不可达，失败很可能来自环境"。
2. **令牌注入**：`test.agent.target-auth.token` 让契约用例带真实登录态。
   此前执行器从不带请求头，需要登录的接口只返回 401/403 —— **假红灯淹没有效信号**。
3. **写路径支持**：`requestBody` 现在会真正下发（此前 `exchange(url, method, null, ...)` 固定空实体），
   query 参数统一 URL 编码（此前手工拼串，边界用例测的是 URL 解析而非参数校验）。

## 7. 缺陷回流：记录型，不是学习型

- 语义断言失败与 5xx 按接口聚合计数、**跨会话持久化**（`test-insights.json`，
  启动加载、上限淘汰、原子写），报告里标注"第 N 次复现"；
- 踩过的坑：快照返回库内对象引用 → 清轮次标记会**反向污染已落盘报告**的 `hitThisRun`；
  修复为深拷贝 + 顺序调整（先 save 再清标记），并写单测锁定时序；
- **主动承认**：`findByApi` 主代码零调用，生成器不读缺陷库 → 下一轮用例与上一轮缺陷无关，
  这是"记录型回流"。

## 8. 质量评测层：把一直闲置的 `referenceAnswer` 用起来

项目原有的召回评测只读 `relevantSources / expectedRefusal / expectedAction / expectedBlocked`，
**149 条 gold 集的 `referenceAnswer` 100% 闲置**，而文档里明确写着
"没有测量通用语义 faithfulness，也没有承诺零幻觉"。这一层就是来补这个洞的。

- 确定性指标（始终计算）：来源命中率、拒答准确率、注入阻断率、动作一致性、P95 时延；
- LLM judge（仅 AI 开启）：答案正确性 / 忠实性，阈值 70；
- **取样策略是类别轮询**：默认 12 条（每条要真跑一次模型 15-25s），轮询保证
  policy/no_answer/injection/boundary/conflict 五类都覆盖 —— 简单取前 12 条会全是政策问答；
- 25 条多轮追问用例**默认排除**：无法可靠复现历史上下文，给出的结论不可信；
- 指标作为一条"质量指标汇总"用例进入报告，前端零改动即可展示。

**五条诚实声明**（建议背下来）：judge 也是 LLM、不构成零幻觉证明；拒答判定是词法匹配；
judge 解析失败记"未评分"而非失败；gold 集是开发者构造需业务复核；judge 默认关闭。

## 9. 三种触发方式：REST / 前端 / MCP

- REST：`POST /api/v1/test/generate?module=xxx`（同步返回报告）；
- 前端：管理后台一键发起（`frontend/src/views/agent/test/index.vue`）；
- **MCP**（`POST /mcp`，协议 `2025-06-18`）：5 个工具
  `list_test_modules` / `run_tests` / `get_run_status` / `get_test_report` / `list_test_reports`。

**MCP 接入的三个设计决定**（可复用）：
1. **异步句柄**：`run_tests` 立即返回 `runId`，轮询 `get_run_status`。
   理由：一轮回归 15~25s/条，同步阻塞会拖死 Agent 客户端。
2. **失败语义分级**：参数错用 `-32602`（协议层），"测试跑出红灯"用 `isError=false` +
   `failedTests` 表达。否则 Agent 会把"发现缺陷"当成"工具坏了"。
3. **上下文体积控制**：`get_test_report` 默认只给摘要 + 失败用例 + 失败断言，
   全量明细要显式 `includeResults=true`；响应体截断到 2000 字符。

**安全立场**：`/api/v1/test/**` 与 `/mcp` 共用 fail-closed 鉴权
（用户 JWT 本地验签 + 内部静态令牌双通道），`module` 走白名单，队列有界且满即拒。
理由：测试 Agent 的最坏情况是"以服务身份对内网系统发任意请求"。

## 10. 报告留存与工程细节

- 内存 + `test-reports.json` 双写（原子写、上限 20 份淘汰、损坏不阻断启动、响应体截断）；
  解决了"MCP 拿到 reportId 后进程重启就查不到"的问题；
- 环境探针结论贯穿 JSON / HTML / 前端；
- 执行器用 HttpClient5 连接池（maxTotal 50 / perRoute 25），
  **连接 5s / 读 10s 分级**，场景对话单独 120s；
- 92 个单测（含协议、守卫、洞察、报告落盘、鉴权），CI 里 `mvn test` 覆盖。

## 11. 短板（主动交代）

1. **默认 AI 关闭** → 只有 4 类规则用例，场景覆盖维度退化；
2. **Schema 断言因 `$ref` 静默失效**；
3. **无重试** → 一次 GC 抖动就是一条红灯；
4. **洞察不学习**；
5. **不测 UI / 并发分布 / DB 副作用**；
6. **无被测代码覆盖率**（`analyzeCoverage` 是死代码，报告里 `parameterCoverage` 曾硬编码 100%）；
7. **报告之间无 diff**：两轮"多红了几个"目前要人看（下一步最该做的）。

## 12. 如果让我继续做

1. **报告 diff 与基线对比**（自动标出"新增失败 / 已修复 / 长期挂账"）；
2. **把质量评测挂进夜间定时任务**（需先解决对 Ollama 的依赖与超时重试）；
3. **flaky 用例识别**：同一用例在多轮中状态抖动就标记为不稳定，避免噪声掩盖真缺陷；
4. **覆盖率对齐**：把 AI 生成用例的分布与 OpenAPI 声明做覆盖度统计，真正回答"测到了什么"。
