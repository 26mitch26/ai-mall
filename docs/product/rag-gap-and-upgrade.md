# AI Mall RAG 能力差距与产品优化

评审日期：2026-10-06。当前项目具备混合检索、版本来源、工具权限、售后确认与评测原型，可以作为 AI 产品经理作品。下一步最有价值的投入是政策适用条件、可验证的服务结果和真实用户闭环。仅有9篇政策与少量合成问题，尚不能证明达到先进 RAG 的通用水平或商业上线标准。

## 对标方法与选择理由

| 参考方向 | 现有能力与差距 | 本项目的选择 |
|---|---|---|
| Contextual Retrieval | 已有 BM25、向量检索与 RRF；仍可能命中正确文档却选错段落。缺少系统性的适用条件上下文实验 | 本轮先做问题驱动的片段选择。后续将标题、业务范围、地区、时间与规则条件附到块上下文，保留原文；有独立验证收益再批量生成上下文 |
| CRAG | 有弱证据判断与纠正路径；相关度不能证明金额、对象、条件正确 | 修复数字重合被当作支持的问题。缺少商城政策时给核对或人工联系指引；不能用互联网上别家规则替代本商城规则 |
| Self RAG | 有输出护栏和证据报告；没有训练反思 token，也没有语义蕴含判定 | 使用便宜的原文核对作为基础检查，语义检查留给抽样评测。不能把规则检查称为完整 Self RAG |
| Microsoft GraphRAG | 当前图按共享政策主题关联文档，不具备完整实体抽取、社区报告和全局查询链路 | 保留可选能力；9篇政策暂不扩大图建设。复杂跨文档任务增多后，对照普通混合检索验证质量与成本收益 |

上述方案解决不同问题，没有一种架构可以直接被认定为本项目的最优方案。2026年的 [RAGRouter Bench](https://arxiv.org/abs/2602.00296) 在其查询与语料组合实验中也发现，固定一种范式不能普遍最优。本项目的技术取舍以商城用户任务、独立评测和成功成本为依据。其他参考：[Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)、[CRAG 原论文](https://arxiv.org/abs/2401.15884)、[Self RAG 原论文](https://arxiv.org/abs/2310.11511)、[Microsoft GraphRAG 查询说明](https://microsoft.github.io/graphrag/query/overview/)。这些资料的实验成绩不是 AI-Mall 的成绩。

## 本轮已修复的问题

| 缺陷与用户影响 | 改动 | 验收依据 |
|---|---|---|
| 99元包邮门槛被用于支持99元运费，地区和否定条件也可能错配 | 数字一致只标为未验证的重合；完整句子匹配才关联支持来源。金额/时效未核对提示在会员端可见 | 门槛与费用、普通与偏远地区、可与不可三个反例被标为未支持；原句引用仍可验证 |
| 第一处关键词或前两段内容容易引入支付噪声、漏掉退款操作 | 按问题主题及操作诉求评分，支持已识别的多主题；找不到某个已识别主题则给出既有缺资料指引 | 配送与支付分离、退款步骤不被前文淹没、退款与发票同时覆盖 |
| “我不知道如何才能拿到退款”没有明确下一步 | 扩展公开政策问法识别，优先引用操作路径；私人订单与退款进度仍走既有业务路径 | Agent 回归验证包含选择订单的步骤，无模型规划、无售后写操作，不声称已退款 |
| 来源预览从文档开头截取，与回答引用段落不一致 | 单独保存本次引用片段，不改原始全文与内容哈希；会员端与管理端区分片段、预览和全文 | 接口回归验证来源内容与引用一致，原文哈希保留；全文加载成功前不标为全文 |
| 筛选出一个来源可能隐藏另一条积分上限 | 积分上限冲突检查同时扫描原始检索结果，冲突拒答保留来源供核对 | 选中50%而另一个来源为20%时拒绝确认，返回两条来源和未接通人工状态 |
| “依据充分”和“工具直查”标签会夸大可信度 | 有来源只说明找到政策依据；无来源不推定真实工具已执行 | 问候回复不会显示工具直查，政策回复提醒核对适用条件 |

片段评分仍是关键词启发式。原句匹配不等于判断原始政策真实、现行、适用于当前订单；合理改写也可能被保守地标为未验证。冲突识别目前覆盖积分抵扣上限，没有通用的跨政策冲突检测器。数值风险提示不等于自动阻断所有错误回答，也不用于否认已验证工具提供的业务事实。

## 验证结果与成本

固定12项合成组件回归从修复前3/12变为12/12。输入是已经检索到的资料，覆盖的是选段、路由、来源与核对行为；不是召回率、业务解决率或端到端语义准确率。用例参与了修复，不能作为新的盲测。前后记录分别在 [修复前](../../eval/results/rag-upgrade/component-before.json) 与 [修复后](../../eval/results/rag-upgrade/component-after.json)。

后端相关模块 Maven package 通过：mall-common 62项、agent-customer 115项，共177项 JUnit 测试，失败0、错误0、跳过0。12个组件断言包含在其中一个 JUnit 测试内，不能与177相加。另有服务响应回归验证冲突来源保留、片段与哈希、无来源标签；本轮未重跑依赖真实 embedding 服务的 RagRecallSemanticTest，不复用历史成绩冒充新测结果。

管理端 vue-tsc 类型检查与 Vite 构建通过，会员端 H5 构建通过；没有声称完成真人交互或已登录业务端到端测试。构建仍有既有大包与 Sass 弃用提示。

本轮验证没有实际调用生成、embedding 或重排模型，没有外部推理 API 费用。后端 JVM 与前端构建串行并限制堆内存；没有删除 Ollama 模型。原有默认模型不变，0.6B 仍只是先前的低成本评测配置。设备、电力和维护成本没有测量，不能宣称总成本为零。

## 产品经理下一阶段优先级

| 优先级 | 要解决的用户问题 | 可执行方案与验收条件 |
|---|---|---|
| P0 | 用户不知道政策能否适用于自己 | 与商家确认政策负责人、范围、有效期及冲突优先级；建立地区、商品、质量责任等条件表。歧义先澄清，不自动断言；让客服复核含例外、过期、冲突的答案 |
| P0 | 收到答复却没有完成退款或得到人工帮助 | 接入测试客服接收端与工单回执，把建议联系、已提交、已接收、已解决分开；保持写操作确认与幂等。用真实登录测试账号验证从咨询到售后状态的完整链路 |
| P0 | 高离线分数无法判断实际可靠性 | 在现有公开问题之外冻结独立的新问法和场景；加入同义改写、缺资料、多轮、复合问题、地区/时间变更和对抗样本。客服双人复核及分歧仲裁；代码断言核对工具副作用与状态 |
| P1 | 不知道升级检索或换模型是否值得 | 在相同知识版本、输入和缓存设置下，对照 BM25、混合检索、上下文补充、小重排及模型规格。预设样本预算，每配置先20次、发现明显退化停止；候选通过后才扩展盲测 |
| P1 | 团队只监控回复量 | 核心指标用验证完成任务数/发起任务数，并拆政策咨询与订单办理；同时看事实正确率、错误办理、越权、再次联系、P95及每成功任务成本。人工接通率要求真实接收回执 |
| P2 | 跨文档任务增长后现有规则不够 | 数据规模与复杂问题比例增加时，再验证图检索、多跳分解与语义校验。上线前分别测增益和失败回退，避免无依据提高模型规格 |

这些是后续工作与验收计划，不能写成已经完成的用户调研、真实接通或线上收益。现在可以完善工程原型；商家政策确认、真实客服渠道和用户反馈需外部参与。

## 面试中如何体现产品判断

可以展开为 STAR：在电商客服原型中，发现正确来源命中后仍可能答错条件，且生成与模型驻留成本受限；目标是在现有预算内提高证据可信度并明确服务边界；将风险拆成数字与条件错配、片段噪声、缺操作步骤和虚假状态，给 AI 明确反例、输入输出与不产生业务写操作的验收合同，再要求实现和回归；12项已知组件缺陷回归由3项通过提升到12项，新增检查不增加模型调用。

个人经历应据实说明：用户提出产品目标、成本约束与评审要求，AI 辅助完成分析、代码和验证。此成果体现问题定义、优先级、技术取舍与验收意识；还需要真实用户研究和业务完成数据，才能支持成熟 AI 产品经理岗位的商业能力主张。
