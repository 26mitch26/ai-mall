# AI-Mall 电商客服 Agent 产品方案

## 定位与用户问题

定位为面向中小电商的售前政策咨询与售后办理助手。购买者希望快速获得可信规则、查到自己的订单，并在理解操作后完成取消或售后申请；客服主管需要知道哪些会话值得交给 AI、哪里必须人工接手；运营维护者需要定位知识过期、工具异常与权限失败。本轮没有真实用户访谈记录，这些是待验证的需求假设，不能写成已完成调研。

项目源于现有 mall 电商骨架，本轮重点是 Agent 产品定义、评测、路由与可靠性迭代。简历只展示一个完整项目，主叙事是“电商客服任务闭环”；运维 Agent 和测试 Agent 是支撑质量与可观测性的后台能力。

## 核心任务与验收

| 任务 | 用户看到的行为 | 产品验收 |
|---|---|---|
| 政策咨询 | 给出适用规则、知识来源和必要限定 | 不编造商家规则，不把公开政策误转成私人订单查询 |
| 我的订单 | 登录后查看当前业务系统的状态 | 身份来自服务端校验，不相信前端传入会员 ID |
| 取消与售后 | 生成草稿，用户确认后才提交 | 拒绝草稿不提交；重试不产生重复业务单 |
| 证据不足 | 说明尚不能确定，给出下一步 | 不能把弱证据答复显示成成功办理 |
| 需要人工 | 尊重用户选择，明确是否真的接入 | 未接 CRM 时不能说“已转接”，本轮仅提供联系指引 |

公开政策选择直答路径，业务状态选择工具路径，写动作选择确认工作流；这些是可解释的成本与安全取舍。0.6B 模型只用作低成本评测对照，是否可替代原模型必须由质量、稳定性与内存共同决定。确定性路由也会漏识别长尾表达，因此保留探索集并记录未覆盖场景。

## MVP 与优先级

MVP 包含政策咨询、订单只读查询、确认后办理、清晰失败信息、会话轨迹与评测报告。本轮已经实现评测资产和部分路由修复；实际 CRM 接入、真实商家试点、埋点闭环仍需后续验证。

| 优先级 | 内容 | 用户价值与验收 | 状态 |
|---|---|---|---|
| P0 | 虚假完成话术修正 | 不声称未发生的转接、办理或退款 | 本轮修复并回归 |
| P0 | 政策发布权限 | 匿名请求无法改变 Agent 的政策依据 | 本轮增加默认拒绝写入的管理员校验 |
| P0 | 政策与业务任务分流 | 配送/支付政策不要求用户先登录私人订单 | 本轮实现并评测 |
| P0 | 低内存运行与成本约束 | 控制上下文、评测隔离归档、请求数，保留中断报告 | 本轮实现 |
| P0 | 业务状态与幂等 | 确认、重试、越权、重复提交有真实状态断言 | 现有流程与集成测试，需持续保护 |
| P1 | 客服真实接入 | 有客服会话/工单 ID 与可验证接收状态 | 未实现；当前明确未接入 |
| P1 | 异常归因与运营工作台 | 失败分为知识、模型、工具、权限和基础设施 | 有部分报告能力；需用户验证 |
| P1 | 埋点与灰度试点 | 明确会话是否被解决、是否再次求助 | 方案已定义，真实数据未采集 |
| P2 | 更广商品推荐/图像售后 | 主流程稳定后验证收益 | 不优先扩大范围 |

没有用户量与真实商业数据时，不用臆造 RICE 的 Reach、Confidence 或 ROI 数字。排序基于失败影响、观察到的错误和实现成本；试点后再用真实任务频次更新优先级。

## 指标与埋点

北极星候选为“每百次客服会话中经业务状态或用户确认验证的解决会话数”。拒答、提供人工联系方式、模型自称已处理，不自动计入解决。分母包括符合实验口径的全部会话；基础设施错误独立分桶并保留在端到端成功率分母。

| 指标 | 定义 | 数据与边界 |
|---|---|---|
| 有效任务完成率 | 有效目标达成数 / 符合范围的会话数 | 业务库结果、工单状态、用户确认；当前暂无线上值 |
| 政策事实正确率 | 事实与本商家当前政策一致的回答数 / 已复核政策回答数 | 双人业务标注，不能以来源命中替代 |
| 自动解决率 | 无人工参与且确认解决的会话 / 全部范围内会话 | 不把拒答计作自动解决 |
| 再联系率 | 解决后约定窗口内因同一问题再次联系的会话 / 被标记解决的会话 | 试点建议先定义 24 小时窗口，再与业务核对 |
| 人工接入成功率 | 获得真实接收状态的转接 / 发起转接请求数 | 当前没有集成，未测 |
| 单次成功成本 | 推理、工具与人工处理等可归因成本 / 验证成功任务数 | 小样本无成功时不报告 0 元成功成本 |
| P95 与重复稳定性 | 端到端耗时；同任务多次都通过的比例 | 同机器/缓存/模型参数下比较 |
| 安全护栏 | 未确认提交、越权读取、重复办理的事件数 | 关键回归为 0，不宣称未知攻击全防护 |

建议事件：session_started、intent_routed、knowledge_retrieved、answer_rendered、human_requested、handoff_acknowledged、draft_prepared、user_confirmed、operation_committed、operation_failed、resolution_confirmed、repeat_contact。记录 session/experiment/task/version/trace 等关联 ID，避免记录令牌。`resolutionStatus` 是回答处理状态；`RESPONSE_PROVIDED` 不代表任务已经完成。原始回答需在受控环境内脱敏保留。

## 验证与灰度

主 KPI 收敛为三项：验证任务完成率、业务复核的政策事实正确率、单次验证成功成本。来源命中、覆盖率、生成调用与时延只作诊断驱动；未经确认提交/越权事件为安全护栏，再联系率为体验护栏。避免靠大量拒答、少走必要步骤或把未解决会话排除来改善主指标。

试点设定中由产品方与客服负责人共同拥有定义，工程负责业务状态和埋点关联；每周复核失败分层与成本，每次发布前执行安全回归。以上是未来运营安排，当前没有实际客服团队或线上业务指标。80% 的离线任务代理门槛是 MVP 工程目标，不能当作用户解决率的基线或商业承诺。

首先执行开发集的路由消融，冻结预留测试集与评分标准，再用预留集验证。语言、检索配置和模型分别报告；失败不能从分母消失。自动判定是词法与结构代理，本轮未有独立业务专家校准。

下一阶段：招募 5–8 位目标用户进行任务观察（人数为计划），每人完成咨询、订单查询、售后确认和人工求助；记录任务完成、理解困难和错误恢复。与 2 位客服人员复核政策答案并评估转接摘要是否可用。通过后在测试商家小流量灰度，以会话为随机单元比较现有服务和 Agent；提前确定任务完成率、再联系率、成本与越权护栏。根据基线、目标最小差异和流量计算样本量，不凭固定百分比宣称显著收益。严重错办立即停用写动作，保留只读与人工渠道。

## 简历竞争力判断

2026-10-07证据更新：215项相关软件测试和7项已知访客回归通过，当前BM25演示与历史语义对照分开报告。本地生成试答因内存不足暂停，云端为模拟验证。补齐会员服务连接配置后，demo账号登录、会员信息和订单列表读取通过；完整下单、支付、售后写入及人工接收仍未验证，不能宣称商城全链路上线。

本项目具备端到端实现、公开数据评测、业务确认与失败迭代证据，适合 AI 产品经理实习/校招叙事。它仍是研发原型，距离有上线与商业收益的经历存在明显差距。最有区分度的证据是：从公开数据暴露的失败，推导产品取舍，执行可复现改进，并清楚说明成本和评测边界。没有招聘样本的统计分析，不提供“击败百分之多少候选人”或就业概率。

只写一个项目时，应保证面试官能看懂用户问题、产品边界、关键取舍、实验设计、失败修复和下一阶段计划。不能把开源 mall 全部功能归为个人原创，也不能将 AI 辅助完成的工程与文档工作全部描述为独立手工开发。个人实际责任、项目周期、学校与经历需本人确认。
