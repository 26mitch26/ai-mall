# AI-Mall 竞品定位与商业验证方案

资料核对日期：2026-10-06。这里区分官方能力资料与产品判断；未实测竞品效果，没有报价、客户访谈或采购合同。

## 竞品与替代方案

| 方案 | 官方可确认能力 | 对本项目的启示 |
|---|---|---|
| 网易七鱼 | SDK 支持机器人/人工会话，API 包含转接关联字段 | 人工接入必须有真实接收状态；本项目的联系指引还不具备这种能力 |
| 阿里云百炼电商客服方案 | 提供问答、RAG、Agent 和复杂流程应用模式 | 按任务选择服务方式，基础平台采购可减少搭建工作 |
| Dify | 知识检索、工作流、Human Input 人参与节点 | 编排平台可用于快速原型，业务 API 与结果验收仍需要设计 |

来源：[七鱼官方 SDK](https://github.com/qiyukf/QIYU_iOS_SDK)、[七鱼会话字段](https://qiyukf.apifox.cn/doc-437028)、[百炼电商客服方案](https://help.aliyun.com/zh/model-studio/build-ai-applications-based-on-alibaba-cloud-model-studio)、[Dify 官方平台](https://www.dify.ai/)、[Human Input](https://dify.ai/blog/the-human-input-node-bringing-human-judgment-into-automated-workflows)。这些资料不支持“竞品没有确认流程”或“自研必然更好、更便宜”的结论。

产品判断：中小商家需要接待渠道、订单系统接入、可靠回答和异常恢复，未必需要重建商城。本项目应把现有电商系统作为验证环境，把带证据的政策服务、确认后的业务动作和可复现评测作为作品重点。商用探索优先接成熟客服渠道并复用业务系统。

## 为什么保留当前工程

现有 Spring 后端便于验证身份校验、业务状态、幂等落库和重试恢复。产品经理据此能解释哪些事实必须读取实时系统、哪些动作必须确认、哪些政策可以原文引用。Dify 或百炼同样可以用于原型验证；当前工程选择服务于业务控制与测试，不证明全部模块都应自研。

## 商业假设

待验证客群是有重复政策咨询、已有订单系统但客服工程能力有限的中小商家。需要核实咨询量、政策复杂度、处理时间、可接入系统、隐私要求、决策人和付费意愿；目前没有可收费需求的证据。

先试点可验收结果，例如约定知识范围内的可信答复与安全售后草稿，而非按 Agent 数量定价。订阅价格和采购收益暂不设数字。

成本模型包括生成、embedding/重排、工具、人工、标注质检、基础设施、集成和维护。成功成本分母必须是已验证成功任务数。本轮生成调用/token 可记录，embedding 用量、电费等未知；云 API 消费为零不代表总成本为零。

经济性应比较同类任务在基线与 Agent 服务中的可归因成本。处理时间减少不自动等于现金费用减少；固定人员成本下，要说明释放时间的用途。真实流量与成本基线到位后再计算 ROI 和回收周期。

## 商业验证顺序

1. 计划观察 5–8 位用户完成任务，邀请 2 位客服核对失败；不是已完成的调研。
2. 接入一个测试商家：真实客服渠道、订单只读 API、测试售后确认流程。
3. 冻结灰度指标：验证完成率、政策事实正确率、成功成本；监控错办、越权和再次联系。
4. 测量可归因时间、解决情况和质检工作量，再决定是否扩展自动办理。

## 岗位竞争力评估

| 维度 | 现有证据 | 仍需补齐 |
|---|---|---|
| 产品定义 | 任务边界、MVP、验收和路线取舍 | 真实用户验证优先级 |
| AI 判断 | 公开数据、重复试验、失败与配置修复 | 双语/业务专家复核、真实分布样本 |
| 工程协作 | 多模块接口、确认、权限与幂等状态测试 | 有身份的完整端到端用户任务 |
| 数据实验 | 指标字典、离线对照、质量成本取舍 | 真实埋点与会话随机灰度 |
| 运营商业 | 官方竞品资料、成本模型与试点计划 | 测试商家、人工渠道与价值基线 |
| 真实性 | 开源来源和未测项明确 | 本人确认职责、周期与 AI 辅助范围 |

判断：适合作为 AI 产品经理实习/校招的单项目作品，有比功能清单更深入的评测与决策证据；目前仍是研发原型，不能与真实用户上线和商业成果等同。没有招聘或候选人样本，不提供领先比例或录用概率。
