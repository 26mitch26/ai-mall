# AI Mall 单项目面试准备

## 三十秒介绍

我围绕政策咨询、本人订单读取和确认式售后定义Agent任务及验收条件，以自建用例和公开合成请求做开发对照，检查答复、工具轨迹和业务状态。评测发现来源命中仍可能答错，因此保留失败并回修；历史开发对照中的文本调用25次降到2次，首次中文预留18/20代理检查通过。后续已知回归和模型配置验证与这次首次成绩分开报告。工程由AI辅助，尚未完成真实商家与用户业务验证。

## 简历三处批注的答辩话术

### 调研了什么，为什么不只写平台名称

百炼、Dify与网易七鱼是桌面研究的竞品/替代能力来源，不是本项目实现了三套方案，也不是三个同类型产品的性能竞赛。

| 对象与资料 | 看什么 | 如何影响本项目设计 |
|---|---|---|
| [百炼应用类型](https://help.aliyun.com/zh/model-studio/application-introduction) | Agent处理开放问题，工作流控制固定步骤，高代码用于定制集成 | 区分政策问答、实时查询与确认办理，不让全部任务自由规划 |
| [Dify Human Input](https://dify.ai/blog/the-human-input-node-bringing-human-judgment-into-automated-workflows) | 工作流暂停，人员审阅/修改后按选择继续 | 写动作先给草稿并要求确认，设计拒绝、异常和恢复路径；未实际迁移到Dify |
| [七鱼官方SDK](https://github.com/qiyukf/QIYU_iOS_SDK) | 机器人会话、人工客服及分配接入 | 人工联系指引与实际接入分开，未有接收回执不说已转接；未接入七鱼 |

上述资料于2026-10-07复核。原百炼电商案例链接本次直接访问返回404，已改用可访问的官方应用类型说明；七鱼API页面本次未能读取，能力判断以官方SDK为依据。没有竞品试用、效果对照、采购报价或客户访谈。

可口述：“我先做官方资料的桌面研究，比较知识回答、流程编排和人工协作。发现客服既要答政策，又要查实时订单，还涉及有风险的办理，所以把MVP拆成有来源的政策回答、鉴权后的订单读取、用户确认后的写动作。调研落到的是任务边界和验收矩阵，不是把几个平台名称列进简历。我没有做过这三个产品的效果跑分，也没有真实客户访谈。”

### P95是什么，为什么正文不写0.6B

P95是把本次请求耗时排序后取95百分位，用于观察较慢请求，而不是平均耗时。该开发实验20次试验用最近秩法，取第19个耗时；28.747s到8.309s只对应同机、同模型与该配置，不能保证线上95%的用户也如此。具体小模型规格、CPU、上下文和缓存设置保留在评测报告，投递正文改写为策略对照、调用与首次预留结果。

可口述：“我验证的是路由策略是否值得保留，不是证明一个小模型已经能商用。同样输入和测试配置下，政策直答与任务分流减少了不必要生成，调用从25次变2次；首次预留20次有18次通过规则检查，失败仍保留。0.6B是当时受预算和内存约束的对照模型，不是上线模型结论。上线前还要按目标模型和业务环境重新测质量、时延、资源与成功成本。”

不写0.6B可以减少与岗位无关的实现细节，但不能据此说完成了大模型商用部署；小模型只说明测试条件，原型/线上区别由用户、业务与验证范围决定。追问实验配置时据实说明，不用“企业级”替代证据。

### 产品调研与设计做了什么

已具备的是官方资料桌面研究、公开合成请求的任务分析、原型失败复盘、MVP及优先级、政策/订单/售后用户路径、权限/确认/异常交互和验收矩阵；证据见 [产品方案](ai-pm-product-brief.md)、[竞争与替代](competitive-and-commercial-plan.md)、[STAR](ai-pm-star-project.md)。没有真实访谈、问卷、商家需求确认或用户实验，不能补写成已经完成。

可口述：“我的设计输入来自竞品官方能力、公开客服请求和原型失败。我先区分政策咨询、实时读取与业务写入，再按错误影响确定优先级，设计正常、缺资料、未登录、拒绝确认和异常路径。开发时给AI这些输入输出、权限和反例验收，评测后依据失败回修。需求频次和价值目前是假设，下一步需要真实买家与客服任务观察验证。”

## 面试追问与证据表

| 追问 | 重点与边界 | 证据 |
|---|---|---|
| 怎样定义Agent成功 | 政策事实需复核；读取看身份和来源；写操作看确认、幂等及业务落库，不能看模型自称成功 | 产品方案、规则与状态测试 |
| 如何证明优化有效 | 同输入、配置、独立会话，保留失败；10种任务各2次，不是20个独立用户 | 历史对照、comparison-provenance |
| 高召回为何仍答错 | 多轮运费、保修、地区时效反例；界面又发现退款离题引用 | 多轮事实记录、ui-smoke |
| 测试都通过就能上线吗 | 模型阶段215项、分块阶段216项及7项已知访客回归覆盖有限范围；需新能力集、业务专家、用户任务与灰度 | 最新总报告与summary.json |
| 模型切换是否真的验证 | 请求参数、隔离和缓存通过模拟HTTP；真实本地试答记录因内存暂停，云端无真实Key测试 | model-selection |
| 哪些业务已经跑通 | 已恢复demo登录、会员信息和订单列表读取；没有验证完整下单、支付与售后提交 | member-login-verification.json |
| 分块为何这样选 | 短语料无法区分256/512；政策章节保护规则与例外，结构8/8不等于语义准确率；旧资料未重建 | chunk-upgrade、Chunk策略审查 |
| 如何指挥AI | 说明任务、输入输出、权限、失败分支与反例验收；用日志和状态证据要求回修 | STAR面试稿 |
| 商业价值如何计算 | 尚无商家试点、用户基线和完整成功成本；调用减少不等于客服财务降本 | 商业验证与指标方案 |

## 可展开的失败故事

1. 缓存配置错位使重复实验不独立；修正并读取服务端配置，旧记录不混入正式对照。
2. 政策直答第一版丢失来源、虚构发票；按失败回修，未通过降低评分条件制造高分。
3. 来源正确却答错条件；添加具体事实与来源片段检查，仍承认它不是通用语义判定。
4. 软件测试通过后，实际界面出现退款误拒答和离题引用；转成已知回归，不重新包装成盲测。
5. 登录页有演示账号不代表后台服务在线；缺少会员服务和数据库连接注入，补齐后只读验证通过，没有重置账号密码。

## 投递边界与下一步

历史368、上下文187、界面193、模型215和分块216是不同范围与阶段，不能累加。40项公开任务来自20条请求的两种语言，首次中文18/20、英文探索3/10均为历史代理检查。不能写“零幻觉”“100%解决率”、真实客户规模、营收、CSAT或未发生的访谈、跨团队人数。

下一阶段补新冻结能力集、人工校准、真实用户任务观察、已登录的完整交易流程、人工接收回执和成本基线。登录成功只是起点；本人须能解释一项技术取舍和一次失败验收，并据实说明个人贡献、开源复用与AI辅助范围。
