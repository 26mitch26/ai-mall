# AI-Mall 项目 STAR 讲解与 AI 协作方法

本稿突出产品经理的场景定义、技术取舍、AI 任务拆解与验收能力。正式简历采用“背景目标—关键行动—验证结果”的 STAR 结构；以下是面试展开。个人职责与周期需据实确认，代码复用开源电商底座并由 AI 辅助研发，不描述为独立手工完成全部工程。

## S 背景与问题

电商客服需要回答平台政策、查询实时订单，并办理有副作用的业务。现有原型把部分问题交给通用模型规划，实验中出现政策咨询误触发私人订单工具、虚构发票生成、声称已经转人工等问题。多轮测试还发现：即使命中了正确来源，也会将人为损坏错说为免费保修、将同城时效错说为一到两天。模型与向量化服务共同驻留又会使约 16GB 机器出现高内存压力。

这些证据来自原型测试，不是已完成的真实客户访谈。产品问题是“如何提供可信、可执行、可验证的服务”，不能以回复流畅或堆叠 Agent 数量代替。

## T 目标与个人职责

将服务拆成“政策有依据、实时数据有来源、写操作有确认、失败有解释、结果可追踪”的任务闭环。以产品负责人视角定义 MVP、优先级、输入输出和验收标准，借助 AI 完成实现与测试，通过实验判断方案能否保留。

产品目标同时包含可信度、任务完成和资源成本。离线代理门槛用于研发验收；真实解决率、满意度和商业降本需要后续商家/用户试点，不使用原型成绩代替。

## A 技术选型如何服务产品目标

| 产品需求 | 选择 | 为什么这样选 | 取舍与边界 |
|---|---|---|---|
| 商家政策可更新、可追溯 | RAG、版本化来源和内容哈希 | 政策事实由当前资料提供，更新不必依赖重新训练模型，出错可以追溯依据 | 没有实测 RAG 与微调的优劣；来源命中不能保证答案正确 |
| 用户问法多样，同时存在精确术语 | bge-m3、Milvus、BM25；需要双路时 RRF 融合 | 语义检索覆盖同义表达，词项检索补精确匹配，融合缓解单路遗漏 | KB 仅9篇，不能声称验证了企业级规模或所有长尾表达 |
| 库存、价格和订单状态实时变化 | 工具 API，复用 Spring Boot 电商系统 | 从业务系统读取，沿用业务权限与约束，避免模型猜测和重复造商城 | 不能把一般政策答复当作已完成订单操作 |
| 取消/售后不能被模型自由触发 | Redis 确认工作流与业务库幂等 | 草稿能跨刷新/重启恢复；确认与重试不能产生重复办理 | Redis/H2 部分边界模拟，完整登录后 E2E 尚需补齐 |
| 长尾诉求需要灵活处理，关键事实需要稳定 | ReAct/模型路径与确定性策略并用 | 模型处理开放表达；已确认政策用原文、人工意图给真实状态，减少不必要生成 | 原文可能冗长，仍需评估切题程度和跨文档条件一致性 |
| 原型预算、硬件受限 | 本地 Ollama，0.6B 对照，驻留与上下文约束 | 控制外部 API 消费，形成质量—时延—资源可比较的实验 | 0.6B 是验证模型，没有默认替代原生产模型；本机总成本未测 |

这组选择说明的是产品约束下的理由，不是“技术越多越好”。没有实际对照过的框架，不宣称性能优胜。运维与测试 Agent 服务于监测、定位和回归，不抢占客服主线。

## A 如何指挥开发 AI

产品经理需要给 AI 可执行、可验收的任务合同：用户场景、目标、可复用组件、输入输出、权限与失败边界、测试条件、交付物。验收看代码、运行配置、业务状态和报告，不能接受“AI 说已完成”作为证明。

本次实际协作中，负责人先明确“单一 AI 产品经理作品、公开相关数据评测、低成本执行、代码与简历产物交付”的目标；发现内存压力后增加资源约束；收到偏工程汇报的简历后，要求改为技术取舍、AI 指挥与效果的 STAR 叙事。具体实现、报告和回修由 AI 辅助推进。面试应区分本人提出的目标与评审意见、AI 产出的方案与代码，不能把每项自动执行说成人工独立完成。

以下是本项目方法的可复用指令模板，不是逐字聊天记录，也不代表实际组织了多个人工研发团队。

### 第一步 让 AI 先理解业务与约束

> 梳理现有客服、订单和售后调用链，列出可复用接口与已知失败。按公开政策、私人数据读取、业务写入分别提出方案；每类给出输入输出、权限、失败处理和验收条件，不先堆技术或扩大范围。

产品经理评审的是：这条路径是否满足用户目标，是否需要实时数据，出错会造成什么损失，是否值得在 MVP 中优先做。

### 第二步 把需求拆成实现任务

> 实现知识检索、工具权限、确认工作流与评测四类任务。库存/订单不得由模型推测；写操作必须经过用户确认；未接入人工客服时不得声称已转接。交付实现、正常/越权/重复确认/重启/异常用例及可复现记录。

产品经理控制模块接口和交付标准。AI 负责代码与测试产物；人负责确认业务规则、风险边界和上线条件。

### 第三步 用失败证据指挥回修

> 固定同一批开发输入、模型和资源配置，读取真实运行参数确认缓存关闭，用独立会话重复试验。保留所有失败，分辨数据、检索、路由、模型、权限和基础设施问题；给出修复前后报告，不调整评分来制造高分。

实际回修案例：政策直答第一版减少调用，却因来源被清空和发票虚构使代理检查降到50%。据此修复来源保留，并将关键政策改为原文引用，再执行开发对照和预留测试。多轮对话命中来源仍答错后，新增三个具体事实回归，而非继续追求召回指标。

## R 达成的效果与正确口径

同一组10类中文任务、各2次开发对照，任务代理检查从13/20（65%）到20/20（100%），文本模型调用25次到2次，减少92%；同机低成本配置下 P95 从28.75秒到8.31秒，降低71.1%。首次中文预留测试18/20（90%）。三组已见多轮事实错误从0/3修复到3/3。

这些是离线必要概念、来源、话术与窄事实回归结果，不是通用语义准确率、线上解决率或财务降本。英文探索3/10，因此暂不承诺英文能力。早期全模块运行记录的368条自动化测试及真实Redis/H2状态验证提供工程证据，不冒充完整真实订单/支付E2E；不同范围的运行不能混加为最新全量成绩。

证据：[实验报告](../../eval/product-evaluation-report.md)、[输入一致性](../../eval/results/comparison-provenance.json)、[首次中文预留](../../eval/results/semantic-test.json)、[多轮事实回归](../../eval/results/multiturn-after-fact-checks.json)。

## 招聘审查后的技术取舍

本轮将历史、检索资料和工具结果纳入字符预算：优先保留完整规则、当前问题与工具轨迹，整份选择政策和近期历史；必需内容超限时停止，而不是截断JSON后继续。未进入模型上下文的资料不能用来事后背书，也移除了相应冗余检索。字符上限不是精确token预算，需要按实际模型校准。相关模块新增10项测试，当前187项通过；没有新增在线模型质量或时延数据。

这项选择体现资源与风险的权衡。Structured Outputs、小型神经重排和多模态检索是条件满足后再对照的候选，当前不能描述为已完成迁移。详细面试追问、技术应用条件和当前简历正文见 [招聘审查](recruiter-review.md) 与 [投递项目段落](resume-project-section.md)。

## 产品经理能力如何被看见

- 场景与优先级：把模糊的“智能客服”转为具体用户任务，按错办影响确定先做什么。
- 技术判断：解释检索、模型、工具、工作流分别适合什么任务，清楚哪些选择尚未验证。
- AI 协作：将需求转换为任务合同，用输入输出、边界和验收约束开发 AI。
- 数据与实验：冻结对照、保留失败，区分代理指标与用户价值，质量回退时能改变方案。
- 产品治理：以权限、确认、幂等、知识版本和真实转接状态管理 AI 的行动边界。

下一阶段优先补真实商家与人工渠道、有身份的完整任务、业务专家标注和用户观察。它们是计划，不写成已经完成的经历。

## Agent 评测方向与界面验收

投递正文新增独立的 Agent 评测设计条目，强调任务与试次定义、冻结输入及运行配置、开发与首次预留集分离、规则评分、工具轨迹与业务状态断言。面对评测岗位追问，要说明这些检查分别能发现什么错误，以及语义判断、业务专家校准和真实用户验证的缺口。

2026-10-07的低内存界面实测发现常见退款问题误拒答，随后又出现命中政策但引用验收条款的离题答复。保留失败后修复BM25高频词权重、历史版本df过滤、低资源排序与时效选段；七项访客回归首次6/7暴露退款步骤缺失，增加公开流程问法扩展后7/7通过。相关193项后端测试通过；这些是已见问题回归，不是新盲测或线上解决率。

界面验证还检查了退款来源版本和全文读取。当前演示为BM25模式，生成调用为0；完整语义部署和登录后的商品、订单、支付链路未在该轮启动。记录见 [界面验收](../../eval/results/ui-smoke/README.md)。这说明单元测试、来源命中和界面“有回复”都不能独立证明任务完成，需按产品成功条件组合验收。
