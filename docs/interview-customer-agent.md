# 三、智能客服 Agent 专项（RAG + ReAct + 护栏）

## 1. 一句话定位

智能客服不是"接了个聊天接口"，而是**在四道护栏内做事实问答**的 Agent：
输入净化 → 意图路由 → 双路召回（RAG）→ 工具取数 → 事实约束 → 输出护栏 → 审计闭环。
模型默认本机 Ollama（零外网、零 Key），可切小米 MiMo / OpenAI 兼容。

## 2. 检索（RAG）为什么这么设计

### 2.1 为什么不能只用向量库
政策类文本里有大量**订单号、金额、专有名词**（"满 99 免运费""7 天无理由"）。
纯语义检索对这些词的召回不稳定，所以加了**词项检索（BM25）**，按问题路由：

- 语义路径：`bge-m3` → Milvus ANN（`ai_mall_kb` collection）；
- 词项路径：Redis 自建 BM25 倒排索引（Set `bm25:inverted:{term}` + Hash `bm25:doc:{id}` + 统计 String）；
- 混合：两条都走 → **RRF 融合** → 特征重排；**神经重排是可选项且默认关闭**（要额外模型依赖，现场优先稳定）。

### 2.2 证据不足就必须拒答
相似度阈值 0.50 未达 → 不把空上下文交给模型，直接拒答/转人工。
这条是"防幻觉"最有效的一招：**不给模型机会，比事后检查更省事**。

### 2.3 知识库是版本化发布的
`rag:revisions:{source}`（ZSet）+ `rag:active:{source}:{scope}`（String）+ `rag:knowledge:epoch`（String），
用 Lua 原子切换。这带来两个能力：**灰度发布**和**精确失效**（语义缓存见第 4 节）。

### 2.4 记忆分了两层，且物理隔离
- 短期会话：`chat:session:{id}`，24h，最多 10 条滚动截断；
- 长期记忆：Milvus **独立 collection** `ai_mall_chat_memory`。
- ⚠️ 为什么必须隔离：如果长期记忆和知识库共用 collection，历史对话会被知识检索命中，
  用户问"我上次说过什么"就会把另一段对话当成"政策依据"——这是很容易被追问的隔离设计。

## 3. 工具调用（ReAct）与鉴权

- 工具分三级：**PUBLIC / USER_DATA / USER_WRITE**，未登录 **fail-closed**；
- 订单类工具必须绑定当前会员并校验归属；
- 每次工具调用进审计（Redis List，7 天，单会话 ≤200 条）；
- 工具描述写进提示词，模型才知道"有什么可调、参数是什么"。

**"我买了哪些东西"这个真实 bug**（实验记录 Failure Case 09）特别值得讲：
用户用口语化问法"我买了哪些东西"，工具集里只有"按订单号查详情"，确定性意图分支也不命中 →
答不出来。修复三步：① 加工具 `list_my_orders`（鉴权登记 USER_DATA）；
② 提示词补工具描述；③ **加确定性分支** `isMyOrdersIntent`（不靠模型猜意图），
并补 3 条会话级回归测试。
> 收获：**口语变体应该用确定性规则兜住，而不是指望模型理解得更准**。

## 4. 语义答案缓存（本项目最"有性价比"的优化）

`SemanticAnswerCacheService`：两级命中——精确（md5(归一化问句 + 上下文键)）与
向量余弦（阈值 **0.92**，线性扫描，容量 **300**，TTL 24h），命中即**跳过整条 LLM 推理**。

三道正确性护栏（这才是缓存敢用的前提）：
1. **会话上下文入键** → 防串答（不同用户/不同上下文不共享答案）；
2. **实时工具数据不入缓存** → 订单状态、价格这类必须实时取；
3. **知识版本 epoch 变更即全清** → 政策改版后旧答案不会继续命中。

命中统计用 `AtomicLong`（exactHits / semanticHits / misses），
`store/invalidate` 用 `synchronized` 串行化。⚠️ 局限：JVM 内存缓存，多实例不共享，
且向量线性扫描在 300 条量级没问题，量级上去要换 ANN 索引。

## 5. 输入与输出两侧的护栏

**输入**：中英文注入模式检测、零宽字符剥离、全角归一化、Base64/URL 编码还原检测。
**输出**：拦截空回答、拦截推理结构泄露（"让我想想…"）、拦截无来源的金额/单号、手机号/身份证 PII 脱敏。
**反馈闭环**：`feedback` 接口 + 人工校对 + 幻觉率统计（Redis 存储）。

**必须说清的边界**：这套护栏挡得住"数字凭空出现"和"注入诱导"，
但**挡不住"语义上看似合理的错话"**。项目文档里明确写了
"没有测量通用语义 faithfulness，也没有承诺零幻觉"——这是我在面试里主动交代的点。

## 7. 追问预案

**Q：为什么要自己做 BM25？用 Elasticsearch 不行？**
A：ES 方案更完备，但要多维护一个组件（默认 profile 里甚至没启动）。自建 BM25 复用现有 Redis，
key 规范清晰、便于教学展示，且我确实需要控制"词项统计更新时机"。代价是功能不如 ES
（无分词器、无同义词扩展——`mall-search` 里用 IK + 同义词规则补上了这块能力，但那是另一个服务）。

**Q：混合检索的融合公式？**
A：RRF（Reciprocal Rank Fusion），按名次倒数加权和，1/(k+rank)，k 常取 60；
它只用**排名**不用分数，避免向量分数与 BM25 分数量纲不可比的问题。特征重排是把两路特征
（是否命中、排名、来源类型）喂给一个轻量模型重新打分，神经重排（cross-encoder）作为可选项。

**Q：怎么防止用户 prompt 里的注入改写系统指令？**
A：输入净化做模式检测与编码还原；真正的防线是**权限**——工具鉴权在服务端做，
模型说什么都不能越权；再叠加输出护栏（PII 脱敏、无来源数字拦截）。
我的观点是"**不要指望提示词防注入，要靠权限边界**"。

**Q：SSE 流式输出怎么做的？**
A：`ChatController` 用 `Executors.newCachedThreadPool()` 推送。
⚠️ 这个池是无界的，生产上应该换成有界池 + 背压；这是我知道但没改的点。

**Q：会话记忆会不会越用越贵？**
A：短期 10 条滚动 + 24h TTL；长期记忆进 Milvus 独立 collection 且检索 topK=5。
成本控制靠语义缓存（命中即跳过 LLM）与阶段级超时分级（检索/生成分别设限）。

## 8. 我会怎么继续改

1. **统一异步治理**：把 SSE、记忆落库、审计落库都收到统一线程池，配监控；
2. **检索质量可观测**：把 `stage` 打点接到面板上，用真实 P95 驱动重排阈值调优；
3. **记忆层补冲突消解**：同一事实两次更新如何收敛（目前只有 append + 检索）；
4. **护栏从词法升级到语义**：引入"答案-证据对齐"打分，把命中来源与答案句子做蕴含校验。
