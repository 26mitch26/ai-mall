## 0. 一句话主线

> **词法 Embedding 纯向量只有 75%，换 bge-m3 中文语义向量后纯向量直接到 87.5%（+12.5pp）；但换语义向量后 BM25 混合反而成了净负数——"混合一定优于纯向量"不能一概而论，优化必须按 embedding 能力取舍。**
>
> 这句话背后是"用评测数据说话、不盲目上优化"的工程方法论。

---

## 1. 起点：召回率为什么低？

面试先讲**诊断**，把问题定位到"检索排序"而非"没召回"：

- 自建离线评测集：**24 条真实客服咨询 / 16 篇知识文档（含 4 篇干扰文档）**，覆盖退货、运费、支付、换货、会员等 12+ 主题。
- 基线（风格纯向量 topK）Recall@1 = **75%**。
- 拆解：真正漏掉的多是**同义改写**——用户说"几天到账"，库里写"退款时效"；说"十五天能换吗"，库里写"换货规则"。词法 n-gram 把这两个文本当成完全不相干，所以排不进 Top1。
- 但要诚实：跑完发现 **Recall@3 已经 91.7%**，说明文档其实都召回了，**瓶颈在排序不在召回**。这决定了后续优化方向（精排、置顶），而不是盲目加路。

> 面试加分：一上来就能区分"召回率组成（@1 vs @3）"，说明你真跑过、不是背概念。

---

## 2. 第一轮优化：混合检索（向量 + BM25 + RRF + 特征精排）

- 双路召回：Milvus 向量捕"退货↔退款"语义，Redis 倒排 + BM25 捕订单号、商品名这类精确词。
- RRF 融合（k=60）免归一化、对异常值鲁棒。
- 特征精排：6 维加权（词覆盖 / 语义相似 / BM25 / 位置 / 长度惩罚 / 查询文档比），模拟真实 CrossEncoder 原理、零 LLM 调用。
- **实测**：Recall@1 **75% → 83.3%（+8.3pp）**、Recall@3 → 100%、MRR 0.823 → 0.910。

> 面试加分：混合检索不是"把两个结果并起来"，而是讲清楚 RRF 为什么不用分数而用排名、精排权重怎么来的。

---

## 3. 两条"看似对、实测有害"的优化——被我们否决了

这一步最能体现思考深度与工程克制：

1. **late-interaction 重排（IDF-MaxSim，2025 年流行玩法）**：
   token 级相似度加权再精排。加了之后 **Recall@1 回退到 66.7%**——因为它和 BM25 的信号高度冗余，二次加权反而放大排序波动。**已回滚。**

2. **Parent-Child 两级分块（子块检索）**：
   短子块参与检索理应收紧语义。但在词法 embedding 下 **Recall@3 从 100% 掉到 95.8%**（子块稀释了父块排序）。**默认不启用。**

> 面试加分：能主动说"我们否决过两个看起来很先进的做法"，并用一条实测数字证明"优化必须经评测确认、绝不盲上"——这比罗列十个技巧更能打。

---

## 4. 机械地拼检索已经到头，真正的天花板在 embedding

- 检索层使劲调到 83.3% 后就上不去了，这是**词法 embedding 的语义上限**。
- 一个关键论证：**英文 embedding 对中文是负资产**。实测 nomic-embed-text / mxbai-embed-large 这类英文模型，中文语义 Recall@1 不升反降（41.7%）——中文必须用中文语义模型。

> 面试加分：说明你做的是面向中国用户的电商场景，"中文语义模型"不是随口说的，是有对照实验的。

---

## 5. 第二轮优化：bge-m3 中文语义向量（本机 Ollama 实测）

- 不引 Elastic/线上 API，直接用本机 `ollama` 跑 bge-m3（`POST /api/embed`，零外网、零 API key），和词法版本**同链路**对比。
- **实测（纯向量单路，不叠任何花活）**：

| 链路 | Recall@1 | Recall@3 | Recall@5 | MRR |
|------|---------|---------|---------|-----|
| 词法哈希 · 纯向量 topK | 75.0% | 91.7% | 95.8% | 0.823 |
| **bge-m3 · 纯向量 topK** | **87.5%** | **100.0%** | **100.0%** | **0.938** |

- 问题**直接从 Embedding 层面消失**：同义改写（"几天到账/多久到账"）被编码成相近向量，纯向量就命中。

---

## 6. 反直觉洞察：换语义向量后，BM25 混合是净负数

这是最关键的观察，也是用户点名要写进简历的那句：

- 词法阶段：混合 ÷ 纯向量 = **83.3% vs 75%（净正 +8.3pp）**。
- 语义阶段：混合 ÷ 纯向量 = **83.3% vs 87.5%（净负 -4.2pp）**。

原因：**语义向量已经覆盖了关键词语义，此时再混进精确字面匹配的 BM25，等于把排序噪声加权进来，稀释语义命中。** "混合一定优于纯向量"是只在词法 embedding 下成立的结论，不能推广。

> 面试加分：同一套检索结构在两代 embedding 下结论相反，说明你是**按能力分场景做取舍**，而不是死记"RAG 就要混合检索"。这句话一出来，思考深度和词法/语义的区别就都立住了。

---

## 7. 收尾：规范主题标签"精确命中置顶"（V5）

- 为文档维护规范主题标签（如 退货→"无理由退货/退款"），查询精确命中标签即置顶。
- 借鉴主流 Skill 检索的 **exact 阶段**思路，属真实生产通用做法，不是逐条作弊规则。
- **实测**：Recall@1 → **91.7%**、MRR → **0.958**，Recall@3 保持 100%。

## 8. 一条完整的优化叙事（30 秒版 / 2 分钟版）

**30 秒版**（电梯陈述）：
> 电商客服 RAG 里，我用一套可复现的离线评测集（24 问 / 16 篇含干扰文档）把召回率从纯向量 75% 优化到 91.7%。路径是：先做双路混合检索到 83.3%，再用 bge-m3 中文语义向量把纯向量直接拉到 87.5%，最后用规范主题标签精确置顶到 91.7%；中途用实测否决了 late-interaction 重排和 Parent-Child 分块两个"看似正确的选择"，并且发现换语义向量后 BM25 混合反而有害——因为优化必须按 embedding 能力取舍。

## 9. 三句话沉淀的方法论（面试"你学到什么"）

1. **区分"没召回"和"排错位"**：先看 Recall@k 的组成，别一上来就盲目加检索路。
2. **一切以评测为准，主动否决无效优化**：技术越热越要实测，late-interaction / Parent-Child 我都用数据证伪过。
3. **换模型优先于调超参**：检索层优化很快碰到 embedding 语义上限，演进 embedding 才是质变；而为中文场景选中文语义模型（bge-m3），有对照实验支撑。
