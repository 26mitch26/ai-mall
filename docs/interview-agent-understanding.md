# 一、我对 Agent 的理解与应用（Agent 专项）

> 这份文档回答三个问题：**什么是 Agent**、**它和普通接口/脚本的区别在哪**、**在本项目里我具体怎么用**。
> 面试时按"定义 → 判据 → 选型 → 落地 → 边界"的顺序讲，最能体现理解深度。

---

## 1. 我理解的 Agent：三个必要条件，缺一不可

很多面试答"Agent = 会调 LLM"，这不够。我用三个可判据的要素定义：

| 要素 | 含义 | 判据（能被追问检验） |
|---|---|---|
| **① 目标驱动** | 不是执行写死的步骤，而是围绕一个目标自行决定下一步 | 去掉 LLM 后，系统能不能自主完成目标？（不能 → 那不是 Agent，是自动化脚本） |
| **② 工具/环境交互** | 能观察环境并施加动作，动作会改变后续观察 | 有没有真实副作用（读文件、查库、调接口、发消息）？还是只在内部自说自话？ |
| **③ 状态与反思** | 记住过程、观察结果、修正下一步 | 有没有 memory / trace / 失败重试 / 自我校验？ |

**一个反例很有说服力**：本项目里 `agent-test` 早期版本的"异常检测 + 报告生成"是一条固定流水线——
发现接口 → 生成用例 → 执行 → 断言 → 报告。它**没有目标驱动的决策**，换个模型也不会改变行为，
所以它是"AI 辅助的自动化测试"，不是 Agent。改造后它才具备 Agent 属性：
**自己决定测什么接口、生成什么用例、哪些失败该沉淀成缺陷、怎么解释红灯归因**（详见测试专项文档）。

## 2. Agent 与传统软件的边界（面试高频）

| 维度 | 传统程序 | Agent |
|---|---|---|
| 流程控制 | 开发者写死分支 | 运行时由模型决策 |
| 期望值 | 唯一正确答案 | 允许多个"可接受答案"，需要评价标准（Rubric / 断言集） |
| 失败模式 | 异常 = bug，栈可追 | 幻觉 = 正常输出，需要护栏兜住 |
| 可测试性 | 断言输入输出 | 断言**性质**（不越权、忠于来源、拒答正确），而非具体文本 |
| 成本结构 | 一次执行恒定 | 与轮次/上下文长度成正比，**必须做缓存与限流** |
| 可解释性 | 调用栈 | 需要额外做 trace / 证据链 / 归因 |

一句话总结：**传统程序把"怎么做"写死，Agent 把"做什么"交给目标 + 约束，剩下靠护栏兜住不确定性。**
所以工程重心从"写逻辑"转移到"写约束与兜底"——这也是我这个项目里工作量最大的部分。

## 3. 我在项目里实际用的 6 种 Agent 能力

### 3.1 单 Agent + 工具调用（ReAct 式循环）
- 场景：智能客服的"意图 → 工具取数 → 组织答案 → 校验"
- 关键设计：**工具权限分级**（PUBLIC / USER_DATA / USER_WRITE），未登录 fail-closed；
  工具描述写进提示词让模型知道有什么可调；每次调用都进审计。
- 反思点：答案必须来自工具或知识库，检索为空直接拒答（不把空上下文喂给模型）。

### 3.2 检索增强（RAG）+ 混合召回
- 场景：客服的政策问答
- 为什么不是"只上向量库"：政策里有大量订单号、金额、专有名词，**纯语义检索会漏词**，
  所以加了 Redis BM25 词项检索，按问题路由：语义 / 词项 / 混合（RRF 融合 + 特征重排，神经重排可选且默认关闭）。
- 知识库版本化：`rag:revisions:*`（ZSet）+ `rag:active:{source}:{scope}`（String）+ 知识版本 epoch，
  Lua 原子切换，支撑灰度与缓存失效。

### 3.3 多 Agent 协作（事件驱动）
- 场景：智能运维的 Monitor → RCA → Heal → Change
- **我做的关键选择**：Agent 之间零直接调用，只通过事件总线（本地同步 / Kafka 双模式）。
- **为什么**：直接调用会让链路变成"一个巨型方法"，任何一环改签名全链路跟着改；
  事件化后每个 Agent 只认自己的输入类型，而且能替换传输层（本地内存 ↔ Kafka）不改业务代码。
- **踩过的坑**：事件乱序会污染状态，所以 `Orchestrator` 里做了状态**单调推进**
  （`advanceStage`：只前进不回退），否则深层环节先完成时会被浅层的后到通知改回中间态。

### 3.4 LLM 作为评测器（LLM-as-judge）
- 场景：客服质量评测（149 条 gold 集，答案正确性/忠实性打分）
- **为什么它有意义**：项目此前的评测只覆盖检索层（Recall@K / MRR），明确写着
  "没有测量通用语义 faithfulness，也没有承诺零幻觉"；judge 补的就是"答案本身对不对"这一层。
- **必须加的护栏**：judge 自身是 LLM，**输出解析失败必须记"未评分"而不是失败**——
  工具故障不能被算成被测对象的质量缺陷。默认关闭（`TEST_AGENT_AI_ENABLED=false`），现场优先可复现。

### 3.5 工具化对外暴露（MCP）
- 场景：让 CodeBuddy / Claude Code 把测试 Agent 当工具调
- 我的认知（这部分很容易被问，也很容易答错）：
  - **API / MCP 是服务端的能力出口，skill 是客户端的使用说明**；
  - MCP 的价值不是"换个协议"，而是**工具语义**：参数 schema、严格校验（`additionalProperties:false`）、
    错误分级（参数错 `-32602`；业务结果红用 `isError=false`）；这些在 REST 里靠调用方自觉；
  - **长任务不能同步阻塞**：一轮真实回归 15~25s/条，Agent 客户端容易超时，
    所以 `run_tests` 立刻返回 `runId` + 轮询 `get_run_status`。
  - **安全立场**：测试侧 MCP 不进网关白名单（协议入口 fail-closed），因为最坏情况是
    "以服务身份对内网系统发任意请求"；而客服侧可以进白名单，因为最坏是"读到他人订单"，
    有逐工具鉴权兜底。**同一个项目里两种策略，取决于能力的后果半径。**

### 3.6 评测闭环（让 Agent 可度量）
- 场景：RAG 召回评测、异常检测离线评测、客服质量评测
- 我的观点：**没有评测的 Agent 不可上线**。三个 Agent 都有可复现的评测口径：
  - 客服：149 条 gold 集，Recall@K / MRR / 拒答准确率 / P50-P95；
  - 测试：92 个单测 + 契约 oracle + 质量指标阈值断言；
  - 运维：20 场景 × 600 点合成序列、固定种子，误报/精确率/召回/F1 与阈值扫描。

## 4. 选型判断：什么时候**不**该用 Agent

这是我认为最能体现工程判断的部分（面试官很爱追问）：

| 场景 | 我的选择 | 理由 |
|---|---|---|
| 异常检测（运维） | **确定性算法**（3-Sigma + EWMA），不用 LLM 判断异常 | 有 ground truth 标注（合成数据），LLM 只会引入不可复现的波动；这类问题属于"有更好算法"的问题 |
| 风险评分、审批门控 | **确定性公式 + 规则** | 涉及安全，必须可解释、可审计、可复现 |
| 期望值（测试的 oracle） | **OpenAPI 声明** | 有客观契约来源就用契约，不用模型猜 |
| 根因归并话术 | 用 LLM | 没有唯一正确答案，需要语言表达 |
| 知识库改版后的语义切换 | 用 LLM | 需要理解意图与表述差异 |

**结论：我的原则是"有客观依据的判定交给确定性代码，只有'需要理解语言'的环节才交给 LLM"。**
LTM 在本项目里还有 3 处硬边界：客服不评"零幻觉"、judge 不评"绝对正确"、运维摘要 prompt 明确禁止编造新指标。

## 5. 我踩过的 Agent 相关的坑（讲 bug 比讲架构更有说服力）

1. **期望值幻觉**：`agent-test` 的 AI 用例生成器会编造"看起来合理"的接口与状态码。
   修复：`TestCaseContractGuard` 以 OpenAPI 声明为唯一 oracle，正向用例锚定文档声明的最小 2xx，
   文档没声明成功码就把用例**作废**（不猜）。
2. **语义键与实体键错配**：运维 RCA 早期拿"上游服务名"（`mysql-primary`）去匹配
   "故障模式 key"，永远匹配不上 → 全部落到默认似然 → 后验退化为 1/N 均分 → 根因定位等于没做。
   修复：给图加 `HAS_FAILURE_MODE {prior}` 关系，并补守卫单测"后验不能均匀化"。
3. **共享引用导致状态污染**：缺陷库快照返回库内对象引用，清轮次标记时会把**已落盘报告**里的
   `hitThisRun` 一起抹成 false。修复：快照改深拷贝 + 调整落库顺序（先 save 再清标记），并写单测锁定时序。
4. **连接噪音被当成产品缺陷**：被测服务没起时满屏红灯，还会沉淀成"已知缺陷"。
   修复：开跑前探 `/actuator/health` 给出归因 + 失败分类器把连接类失败判为噪音。
5. **算法自我吸收**：持续故障会让 EWMA 基线慢慢漂移，最终"故障变成常态"。
   修复：异常点用更小的 α（0.02）+ 连续 50 个异常点才重建基线。
6. **自定义 SDK 默认值踩坑**：Milvus SDK 默认 `idleTimeout=30s` 导致通道被回收，
   30 并发下失败率 46.72%。修复：显式建 client（180s + keepalive）。
   这条虽不是 Agent 问题，但同样说明"默认值不能想当然"。

## 6. 如果让我继续做（回答"下一步规划"）

1. **记忆分层**：现在只有短期会话（Redis，24h，10 条滚动）+ 长期记忆（Milvus 独立 collection），
   缺"用户偏好/画像"这一层，而且缺记忆的**遗忘与冲突消解**策略（同一事实两次更新如何收敛）。
2. **工具调用的成本治理**：可以做"工具结果指纹缓存"（同参数短时不重复调外部接口），
   以及"并发工具调用"（现在串行）。
3. **Agent 自评测闭环**：让测试 Agent 的失败分类反过来指导客服的提示词/知识库补齐，
   而不是靠人翻报告。
4. **可观测性**：trace 里加上"哪一步贡献了最终答案"的归因（现在是阶段级 Timer + outcome tag）。

> 客服负责在护栏内回答，测试 Agent 负责发现回归，运维 Agent 负责发现异常并给出建议；
> 它们共同的工程原则是——**有客观依据的判定用确定性代码，需要理解语言的环节才用 LLM，
> 而任何输出都要有可验证的判据**。"
