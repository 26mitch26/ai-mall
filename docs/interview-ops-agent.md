# 五、智能运维 Agent 专项（检测 → 归因 → 建议 → 门控）

> **2026-10-07核验：** 本文保留早期工程/选型阶段的记录，未重测的数值不是当前结果。当前任务评测、模型入口、分块与登录状态以 [产品评测报告](../eval/product-evaluation-report.md)、[最终实验报告](../实验报告-最终版.md) 和 [Chunk策略审查](product/chunk-strategy-review.md) 为准。旧子块实验不否定完整父段恢复；历史来源命中与测试通过不能当作真实解决率。


> 这套系统最容易被追问"到底能不能自动修故障"。我的答案是：**不能，而且我主动说**。
> 这篇文档讲清楚它到哪一步、为什么停在这、以及每一步的实现与取舍。

---

## 1. 定位：现在能到"发现 + 归因 + 建议 + 审批"

| 能力 | 状态 | 依据 |
|---|---|---|
| 发现异常 | **能（给定指标流）** | 3-Sigma + EWMA 双算法投票，有离线评测背书 |
| 主动感知 | **现在能（配置后）** | 上报端点 + 定时拉取目标 `/actuator/metrics`；默认不配置则不产生外部请求 |
| 根因定位 | **半能** | Neo4j 图遍历是真的；先验/似然是代码常量，朴素贝叶斯假设独立 |
| 处置建议 | **能** | 7 个 Playbook 关键词匹配 + L0/L1/L2 分级 |
| 执行修复 | **不能** | 模拟推演（simulated），无 K8s/发布平台/SSH 任何执行器依赖 |
| 变更门控 | **有闭环** | 风险评分 + 四档审批 + 可落盘审批单 + 批准/驳回接口 + 前端可操作 |
| 审计 | **半成品** | 门控审批单落盘 JSON；Agent 事件走事件总线（可回放） |

停在这一步的原因很实在：**演示环境不该真重启服务**。要接真实执行器，只需替换
`SimulatedExecutor` 的实现，链路其余部分不变。

## 2. 异常检测：算法与两个关键工程细节

- **3-Sigma**：滑动窗口（60）真实均值/标准差，`zScore = |value-mean|/stdDev > 3.0`；
- **EWMA**：动态阈值 `μ + 3σ`（方差只在正常点更新），单边判上界；
- **AND 投票**：需双算法同时触发。

**取代价（要主动说）**：离线评测（20 场景 × 600 点、固定种子、可复现）显示 AND 投票相对单算法
显著降低误报，精确率 92.31% → 94.61%，但**召回从 39.24% 掉到 15.53%，F1 低于单用 3-Sigma**。
这是"告警疲劳场景下用召回换精度"的有意识取舍，不是嘴上的加分项。

**两个防"算法自我说服"的设计**（真实踩坑）：
1. **异常点用更小的 α（0.02）**：防止持续故障被 EWMA 慢慢吸收成新常态；
2. **连续 50 个异常点才重建基线**：否则故障期会被当成正常；
3. 检测**必须先判后更新状态**，避免自参考污染。

**冷启动**：窗口最小样本 10，不足则跳过检测（避免启动即误报）。

## 3. 指标从哪来（三条路径，默认零副作用）

1. **上报端点** `POST /api/v1/incidents/metrics`：采集器/被监控服务推送指标点；
2. **主动巡检**：`@Scheduled` 定时 GET `{baseUrl}/actuator/metrics/{metric}`，
   取 `VALUE` 统计量；**targets 只允许来自配置文件**（`baseUrl|metric|service`），
   **不接受请求参数传 URL** —— 否则就是 SSRF 入口；
3. **手工注入** `POST /trigger` 供课堂演示：`demo_mode` **默认 false**，
   不再"默认路径就在伪造基线"。

采集到的点同时回写 Micrometer（`aiops.metric.{name}` Gauge），能被 `/actuator/prometheus` 抓走，
形成"采集 → 检测 → 可视化"闭环。

⚠️ 拓扑仍是**代码里的常量**（8 服务 / 7 依赖 / 40 个先验概率），要接生产得换 CMDB/注册中心数据源。

## 4. 根因分析：图 + 朴素贝叶斯（含一个真实 bug 故事）

**五步**（`RCAAgent`）：影响链 → 候选根因 → 贝叶斯推断 → 选根因 → 给建议动作。

- **图是真图**：`MATCH path=(s)-[:DEPENDS_ON*1..5]->(d)` 变长路径取影响链；
  `MATCH (up)-[:DEPENDS_ON*0..3]->(s)` 向上游回溯取故障模式；
  Neo4j 不可用 → 降级为内存 BFS 等价实现；
- **"贝叶斯"是朴素贝叶斯**：`P(cause|alert) ∝ P(alert|cause)·P(cause)`，条件独立假设，没有 CPT、没有结构学习。
  这一点我一定主动说，因为它很容易被误讲成"贝叶斯网络"。

**一个值得讲的 bug**：早期版本拿"上游服务名"（`mysql-primary`）去匹配 CPT 的"故障模式 key"，
永远匹配不上 → 全部落到默认似然 0.05 → 后验退化为 1/N 均分 → 根因定位等于没做。
修复：给图加 `HAS_FAILURE_MODE {prior}` 关系，让候选根因**自带故障模式与图上先验**，
并补了一条守卫单测："后验不能均匀化"。

> 面试价值：讲"我曾经把贝叶斯网络讲得比实际做的更强，后来发现后验被均匀化，
> 于是加了一条断言把它钉死"——这比展示任何架构图都有说服力。

## 5. 多 Agent 协作：事件驱动 + 状态单调推进

```
Orchestrator.triggerIncident() 只调 MonitorAgent.detectAnomaly()
MonitorAgent --AlertEvent--> aiops.alerts  --> RCAAgent
RCAAgent     --RCAResult --> aiops.events  --> HealAgent
HealAgent    --HealAction--> aiops.commands--> ChangeAgent
ChangeAgent  --ChangeDecision--> aiops.audit --> Orchestrator 汇聚 IncidentState
```

- **Agent 之间零直接调用**（可用 `findReferences` 验证：RCAAgent 不持有 HealAgent 引用）；
- `EventBus` 双模式：`local-mode=true`（默认，发布线程内同步分发，便于演示与测试）/
  `false`（Kafka，四个 topic + 四个消费者组 + `earliest`）；
- `Orchestrator` 职责收缩为"状态汇聚"，且 `advanceStage` **保证状态单调前进**：
  事件驱动下乱序到达不会把终态改回中间态（深层先完成时被浅层后到通知覆盖）。

⚠️ 诚实说明：Kafka 路径**默认关闭且演示时没真跑过**（`listener.auto-startup: false`）。
本项目用 `docs/docker-footprint.md` 明确标注"Kafka 是 opt-in profile"。

## 6. 处置建议与门控闭环

- **7 个 Playbook**（rollback / restart / scale_out / clear_cache / disk_cleanup / network_repair / failover），
  匹配打分：根因关键词命中 +0.4/个、动作名匹配 +0.3、置信度适配 +0.1~0.2；
- **分级**：置信度 >0.7 且评分 >0.8 且爆炸半径 <0.3 → L0_AUTO；置信度 <0.4 或半径 ≥0.6 → L2_APPROVAL；
- **风险评分** = 0.35×爆炸半径 + 0.25×级别风险 + 0.25×(1-历史成功率) + 0.15×影响服务数，
  四档阈值（0.3 / 0.6 / 0.8）对应 auto / 值班工程师 / 团队负责人 / CTO。

**门控是"默认放行"的**（低风险直接自动通过），所以我补了闭环：
需要审批的门控生成**可落盘的审批单**（原子写、损坏不阻断、上限淘汰），
支持 `GET /gate-decisions?status=pending_approval` 与 `POST .../approve|reject`，
前端可直接操作。**批准后回写历史成功率** —— 此前 `updateSuccessRate` 零调用方，
风险评分里那个因子恒为默认 0.5，是块纯装饰。

## 7. 模拟执行器：明确标注，不伪装

- 逐条推演 playbook 步骤，输出 `ExecutionRecord`（每步耗时固定公式 → **可复现**，不引入随机数）；
- 对 playbook 声明的验证条件给出"可否判定"结论，字符串里明确写"**未真实执行**"；
- 匹配不到步骤定义时**判失败而不是成功**（这是"需要人关注"的信号）；
- `dryRun()` 也从"无条件 `return true`"改成真实判定（步骤为空/含占位步骤 → 失败），
  使 `dry_run_failed` 分支第一次可达；
- `playbook.steps` / `verification` 首次被真实消费（此前只出现在日志里）；
- `aiops.execution.mode=disabled` 可只审批不推演（纯审批演练）。

## 8. 我修过的部署与配置事实性缺陷（这一节很像"运维经历"）

| 问题 | 影响 | 修复 |
|---|---|---|
| 部署清单把 ops 写成 8083（customer 的端口） | 探针/抓取全指错服务 | 8 处配置改 8084 |
| ops 模块无 actuator 依赖 | 探针必然 404 → K8s 判死 → 永不重启 | 加 `spring-boot-starter-actuator` |
| 补上 actuator 后 Redis/Neo4j 未起 → health 503 | 可选依赖把探针打成不健康，Pod 被反复重启 | 健康口径改为只反映自身存活（liveness/readiness 只含 ping） |
| `/agent/ops/**` 网关无限流，而触发接口内含同步 LLM 调用（可达 60s） | 廉价 DoS 面 | 加 `RequestRateLimiter` 3/6（按下游成本分级） |
| `@Scheduled` 因缺 `@EnableScheduling` 永不执行 | 检测统计与巡检是死代码 | 加注解 |
| 注释与配置相反（"kafka 模式（默认，生产）"实际默认 local） | 误导维护者 | 改注释 |

## 9. 追问预案

**Q：为什么用 AND 而不是投票/加权？**
A：加权投票需要一个"谁更权威"的先验，我没有依据；AND 是最保守的——牺牲召回换精确率。
如果误报是主要痛点，AND 合理；如果漏报是主要痛点，应该单用 3-Sigma 或改 OR。
**关键是把这个取舍显式化并能量化**，而不是凭感觉。

**Q：怎么评估检测效果？**
A：合成序列 + ground truth（20 场景 × 600 点，固定种子可复现），指标有误报率、精确率、召回、F1，
以及阈值扫描（1.5~3.5）找正收益区间。⚠️ 这是**合成数据**上的结论，不能当成生产效果。

**Q：告警风暴怎么办？**
A：目前靠双算法 AND 抑制 + 缺陷库聚合（同接口反复失败聚合计数而不是每次都响）。
⚠️ 真实的降噪（抑制窗口、聚合规则、值班排班）没做——这属于 TODO 而非已实现。

**Q：为什么不用现成的 AIOps 平台/开源方案？**
A：这是课设，目标是走通"检测→归因→建议→门控"每一步的判定逻辑并留下可复现证据；
用现成方案会把这层逻辑变成黑盒。生产上显然应该优先接 Prometheus + Alertmanager。

## 10. 我会怎么继续做（按优先级）

1. **降噪与值班闭环**：抑制窗口 + 聚合规则 + "同一根因 5 分钟内合并"；
2. **真实执行器**（放最后，且必须显式开关 + dry-run 沙箱 + 变更窗口约束）；
3. **先验数据源改造**：拓扑与先验从 CMDB/注册中心拉，而不是代码常量；
4. **从静态拓扑到动态拓扑**：服务实例级影响面（而不是服务级）；
5. **把事件总线真跑一次 Kafka**（含重试与死信），验证异步语义下的状态收敛。
