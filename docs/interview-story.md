## 1. 30 秒电梯陈述（自我介绍开场）

> "我做的是一个 **AI 增强的电商系统**，Java 21 + Spring Boot 3.5，6 个业务服务加网关，
> 三个模块用 Agent 的方式做 AI 能力：**智能客服**（RAG + ReAct + 四道护栏）、
> **自动化测试**（OpenAPI 契约驱动 + 会话场景 + 质量评测）、
> **智能运维**（双算法异常检测 + 图归因 + 变更门控）。
> 我的关注点不是把模型接进来，而是**怎么让 AI 能力可度量、可归因、可兜底**——
> 比如测试 Agent 用 OpenAPI 声明当唯一 oracle，避免期望值靠猜；
> 客服承认"挡得住数字凭空出现，挡不住语义错话"；
> 运维的执行环节是模拟推演，不假装能自动修故障。"

**为什么这样开场**：先给结构和判断力，再给细节。面试官听到"可度量、可归因、可兜底"会立刻知道
你不是在堆功能。

## 2. 3 分钟项目介绍（结构化）

**① 背景与定位**（20s）
电商系统（会员/商品/购物车/订单/营销）作为业务底座，上面挂三个 Agent 模块。
目标是让 AI 能力**在工程上站得住**，不是做 demo 页面。

**② 智能客服**（40s）
- 检索：向量（bge-m3 → Milvus）+ 词项（Redis 自建 BM25）按问题路由，混合用 RRF 融合 + 特征重排；
  神经重排可选、默认关闭。证据不足直接拒答，不给模型幻觉机会。
- 工具：PUBLIC / USER_DATA / USER_WRITE 三级鉴权，未登录 fail-closed。
- 护栏：输入净化（注入/零宽/编码还原）→ 输出护栏（空回答/推理泄露/无来源数字/PII）→ 审计闭环。
- 性能：语义答案缓存（精确 + 向量 0.92，三道正确性护栏），命中跳过整条 LLM 推理。
- 自曝边界：挡得住数字凭空出现，挡不住语义错话；不承诺零幻觉。

**③ 自动化测试**（50s）
- 四层：契约层 / 会话场景（11 条）/ 质量评测（149 条 gold）/ 缺陷回流。
- 核心设计：**OpenAPI 声明是唯一 oracle**——文档没声明成功码就把用例作废，不猜；
  AI 幻觉出的方法/路径/参数/状态码逐一拦截。
- 让红灯可信：开跑前探 `/actuator/health` 区分"环境挂了"与"代码坏了"；
  失败分类器把连接噪音与真缺陷分开。
- 触发：REST / 前端 / **MCP**（外部 Agent 可当工具调用，fail-closed 鉴权）。
- 真实战果：扫出 4 类线上级缺陷（负分页触发 SQL 500、网关路由缺失、Mongo 未启动致三接口 500、
  未知路径被伪装成 500），全部修复。

**④ 智能运维**（40s）
- 检测：3-Sigma + EWMA **AND 投票**（窗口 60 / 最小样本 10 / α 0.3、异常点 0.02），
  **用召回换精度**（误报降 73~86%，召回 39.24%→15.53%，F1 低于单算法），取舍显式化。
- 归因：Neo4j 图遍历 + 朴素贝叶斯（有图先验关系 + 守卫单测"后验不能均匀化"）。
- 门控：风险评分 + 四档审批 + **可落盘审批单** + 批准/驳回 + 回写历史成功率。
- 执行：**模拟推演**，明确标注"未真实执行"；无真实执行器是刻意选择。
- 主动交代：指标面默认不主动发请求；部署端口 8083→8084、健康检查语义等事实性缺陷是我修的。

**⑤ 工程与反思**（10s）
6 个 AI 相关单测组共 136 个（客服 + 测试 92 + 运维 44）；三个模块的所有 AI 决策都配了
"可复现的评测口径"；短板我都能当场说出来（见第 5 节）。

## 4. 六个 STAR 故事（面试讲故事的弹药）

### 故事 1：契约绿≠功能可用（最有含量）
- **S**：客服演示时用户问"我买了哪些东西"，接口全通，但 Agent 答不出来。
- **T**：判断是缺陷还是需求缺口。
- **A**：定位到三个断点——工具集只有"按单号查详情"、口语化问法不命中确定性意图分支、
  **自动化测试只覆盖契约层**。修复：加工具 + 补确定性分支 + 补 3 条会话回归 + **新增场景套件**。
- **R**：把"契约层与会话层互补"写进代码注释与文档，成为后续两套测试的设计依据。
- **想讲的点**：**测试的盲区要用测试来补，而不是用嘴解释**。

### 故事 2：期望值治理（体现工程思维）
- **S**：AI 用例生成会编造看起来合理的接口与状态码。
- **T**：让 LLM 生成的用例可信。
- **A**：引入 `TestCaseContractGuard`，以 OpenAPI 声明为唯一 oracle；正向锚定最小 2xx、
  未声明成功码则作废；四类幻觉逐一拦截；补 12 条守卫单测。
- **R**：AI 用例从"不可信"变成"可复现地可信"，现场可开可关。
- **想讲的点**：**引入 LLM 后，第一件事是给它套约束，而不是给它更多权力**。

### 故事 3：后验被均匀化的 bug（体现调试深度）
- **S**：根因分析结果看起来"每次都一样"，像随机。
- **T**：找出为什么贝叶斯推断没起作用。
- **A**：拿"服务名"去匹配"故障模式 key" → 永远匹配不上 → 全落默认似然 → 后验退化为 1/N。
  修复：给图加 `HAS_FAILURE_MODE{prior}` 关系 + 守卫单测"后验不能均匀化"。
- **R**：根因定位从"随机"变成稳定命中预期故障模式。
- **想讲的点**：**当 AI 系统输出"看起来像那么回事"时，要用断言去验证它，而不是调 prompt**。

### 故事 4：共享引用污染已落盘数据（体现严谨）
- **S**：报告里"本轮命中"永远是 no。
- **T**：定位一个只有时序错配才会出现的现象。
- **A**：两处原因——① `markRoundCompleted()` 早于 `save()`；② 缺陷库快照返回**库内对象引用**，
  清标记时把已保存报告里的字段一起抹了。修复：快照深拷贝 + 调整顺序 + 单测锁定时序。
- **R**：报告正确显示"第 N 次复现"，且这类问题以后不会复发。
- **想讲的点**：**顺序 bug 需要用测试固定顺序，而不是靠代码评审"看着没问题"**。

### 故事 5：健康检查语义设计（体现可用性意识）
- **S**：K8s 里 ops Pod 一直不健康。
- **T**：为什么明明加了 actuator 还是不健康。
- **A**：两个错误叠加——① 部署清单把 ops 端口写成 8083（customer 的端口）；
  ② 补上 actuator 后 Redis/Neo4j 未起让 health 返回 503，而这两个对本服务是**可选依赖**
  （Neo4j 有内存降级）。修复：8 处端口改 8084 + 健康口径只反映自身存活。
- **R**：探针恢复正确；我由此形成一个认知：**健康检查的语义设计本身就是可用性设计**。
- **想讲的点**：**探针不是"配了就行"，它表达的是"什么条件下这个服务算活着"**。

### 故事 6：把"能演示"和"能上线"分开（体现工程判断）
- **S**：演示模式下发现默认路径就在伪造基线，且 Playbook 的 dry-run 无条件返回成功。
- **T**：这些在演示时是"优点"，在追问时是"硬伤"。
- **A**：`demo_mode` 降为显式开关（默认 false）；dry-run 改为真实判定；执行环节明确为
  `simulated` 并在接口与文档里标注"未真实执行"；**刻意不提供 real 模式**。
- **R**：所有边界都有据可查，面试时能正面回答"能不能自动修复"。
- **想讲的点**：**诚实标注边界不是削弱项目，而是让可信的部分更可信**。

## 5. 三个"不要说的话"

| 不要说 | 为什么危险 | 改说 |
|---|---|---|
| "我的运维 Agent 能自动修复故障" | 一追问就露馅（无执行器） | "能发现、能归因、能给建议与模拟推演，真实执行器是刻意留空的" |
| "我用贝叶斯网络做根因定位" | 实际是朴素贝叶斯 | "朴素贝叶斯 + Neo4j 图遍历，先验来自图上关系属性" |
| "实验报告里有运维的效果数据" | 报告里搜不到运维内容 | "运维侧可引用的数字是 README 那组离线评测：20 场景×600 点、固定种子" |

其他慎用词："零幻觉"、"高准确率"、"优化了性能"（没数据就别用）、
"微服务架构"（我们是多模块单体 + 网关，不是真正的微服务）。

## 6. 面试节奏建议

- **前 5 分钟**：让面试官选感兴趣的方向（后端 / AI），再按 `interview-backend.md` 或
  `interview-agent-understanding.md` 展开；
- **中途被问"这个项目的难点"**：讲故事 1（契约绿≠功能可用）或故事 3（后验均匀化）；
- **被问"有什么不足"**：直接说短板清单（记录型回流、无真实执行器、LLM 用例不可复现、
  无覆盖率门禁），并说清下一步计划；
- **最后 2 分钟**：主动说"如果让我继续做，我会先做报告 diff 和 flaky 识别，
  因为它们能让这个测试系统从'能跑'变成'可信'"。
