## 0. 先把三个常被说混的概念讲清楚（最容易被追问，也最容易讲错）

### Q：你们的测试 Agent 是被外部 Agent（比如 CodeBuddy）调用的吗？那不就是 skill 吗？还是内部 API？

**答**：三种都用了，但它们解决的是不同问题，边界是这样的：

| 形态 | 是什么 | 在本项目的位置 | 典型用途 |
|---|---|---|---|
| **内部 HTTP API** | 普通 REST 接口，服务自己提供能力 | `POST /agent/test/api/v1/test/generate?module=xxx` | 前端按钮、CI 脚本 |
| **MCP（Model Context Protocol）** | 给 LLM 用的标准协议，暴露 `tools/list` 和 `tools/call`，让任意 MCP 客户端把服务当工具调用 | `POST /agent-test/mcp`（Streamable HTTP，协议版本 `2025-06-18`） | 让 CodeBuddy / Claude Code 把"跑一轮回归"当工具用 |
| **Skill** | 客户端侧的约定：一段提示词 + 一个脚本，作用是**告诉 Agent 什么时候用、怎么用** | 仓库里没有（也不该有） | 封装"一键跑回归并解读报告"的使用方式 |

关键区别一句话：**API 和 MCP 是服务端的"能力出口"，skill 是客户端的"使用说明"**。
skill 不能替代鉴权，也不能让一个服务变成工具——它只是包装。真正让外部 Agent 能调用的是 MCP 端点。

**我们项目的选择**：
- REST 是基础能力，前端走它；
- 额外做了 MCP 端点，因为发现"只有按钮能触发"的测试系统没法被 Agent 编排；
- **MCP 端点没有进网关白名单，而是 fail-closed 要求凭证**。客服侧的 MCP 端点是公开入口 + 逐工具鉴权，
  但测试侧最坏的情况是"以服务身份对内网系统发任意请求"，所以协议入口本身就要 JWT 或内部静态令牌。

**要准备好的追问**：
- "为什么不直接开个 REST 接口给 Agent？" → REST 当然可以，MCP 的价值在于**工具语义**：
  参数 schema、参数校验（`additionalProperties: false`）、错误分级（参数错用 `-32602`，
  测试跑出红灯用 `isError=false`），这些在 REST 里要靠调用方自己约定。
- "MCP 和普通 REST 的性能差异？" → 差别在会话与传输层。本项目用的是 JSON-only profile，
  刻意不做 SSE 事件流与会话恢复，因为测试任务是"一次调用拿一个报告"，长任务用
  `run_tests` 立刻返回 `runId` + 轮询 `get_run_status` 的方式解决（Agent 客户端最容易死在同步阻塞上）。

### Q：LLM 在你们这套系统里到底做什么？

**答**：分工写死在代码里，不是"哪里都能加个 LLM"：

| Agent | LLM 的角色 | 不交给 LLM 的部分 |
|---|---|---|
| 智能客服 | RAG 生成 + 工具调用后的答案组织 | 检索路由、工具鉴权、答案必须落在工具/知识库结果上、输入净化、输出护栏 |
| 自动化测试 | 用例扩写（默认关闭）、LLM judge 打分 | 期望值来源（OpenAPI 声明）、断言、噪音分类 |
| 智能运维 | 只生成根因摘要（≤120 字），且 prompt 明确禁止编造新指标 | 双算法检测、图遍历、朴素贝叶斯、风险评分、审批门控 |

一句话：**LLM 只在"需要语言理解"的地方用（生成、摘要、语义打分），凡是有客观依据的判定都交给确定性代码。**
这是我在面试里最想强调的一条设计原则。

## 1. 智能客服 Agent（RAG + ReAct）

### Q：讲一下整体链路。
**答**：输入净化 → 意图路由（确定性关键词优先）→ 两条召回路径（`bge-m3` 向量 ANN / Redis BM25 词项）
按问题路由，混合检索用 RRF 融合 + 特征重排（神经重排可选、默认关闭）→ 工具调用取事实（会员数据、订单）→
事实约束（答案必须来自工具或知识库，检索为空直接拒答）→ 输出护栏（拦截空回答、推理结构泄露、
无来源的金额/单号、PII 脱敏）→ 全链路审计留痕（Redis）。模型默认本机 Ollama，可切小米 MiMo / OpenAI 兼容。

### Q：怎么保证"不乱说"？
**答**：四道防线 + 一个诚实声明：
1. **输入净化**：中英文注入模式、零宽字符剥离、全角归一化、Base64/URL 编码还原检测；
2. **事实约束**：检索为空不把空上下文交给模型，直接拒答；
3. **工具鉴权**：PUBLIC / USER_DATA / USER_WRITE 三级，未登录 fail-closed，订单查询绑定用户并校验归属；
4. **输出护栏**：无事实来源的金额/单号、手机号身份证脱敏；
5. 人工校对闭环：`feedback` 接口 + 幻觉率统计。

诚实声明：**这不等于零幻觉**。词法证据校验能挡住"数字凭空出现"，但挡不住"语义上看似合理的错话"——
所以项目文档里明确写了"没有测量通用语义 faithfulness，也没有承诺零幻觉"。
后来在测试侧补了 LLM judge（见第 2 节 Q6），但那是趋势指标，不是零幻觉证明。

### Q：RAG 效果怎么证明的？
**答**：三层证据，注意区分哪些是真实数据、哪些是合成数据：
- 真实：`docs/rag-recall-validation.md` 的召回评测（`scripts/evaluate-customer.py`），
  149 条 gold 评测集、固定随机种子、输出 Recall@K / MRR / precision@K / 拒答准确率 / P50-P95 时延；
- 合成：注入异常实验（人为把响应延迟/错误率拉高，看监控能否发现）；
- 回归：改完 bug 跑全量用例数（58/58、63/63、场景 11/11）保证不退化。

**不能说的话**：不要说"召回率 98%"这种没核对的数字；被问具体数字时，只报测试类名和口径。

## 2. 自动化测试 Agent

### Q：接口全绿就等于功能可用吗？
**答**：不等于，而且这个项目里就有真实案例。实验记录 Failure Case 09：
用户问"我买了哪些东西"，契约测试 14 条全绿，但会话链路答不出来——因为契约层只验证
"HTTP 接口存在、参数与状态码行为"，不覆盖"口语化问法 → 意图命中 → 工具取数"这条会话级路由。

所以我做了三件事：
1. **契约层**：用 OpenAPI 声明作为**唯一 oracle**。正向用例锚定文档声明的最小 2xx；
   文档没声明成功码就把用例作废（不靠猜）；负向用例按声明精确断言或降级为 4xx 弱断言。
   AI 生成的用例会被契约守卫拦截幻觉的方法/路径/参数/状态码。
2. **场景层**：11 条数据驱动用例（意图、必含/禁含词、知识来源数、401 鉴权边界、"只确认不建单"）。
3. **质量评测层**：149 条 gold 评测集上算来源命中、拒答准确、注入阻断；开启本地模型后追加
   答案正确性/忠实性打分。这是补上"一直没人评答案"的缺口。

### Q：怎么区分"代码坏了"和"环境挂了"？
**答**：开跑前先探 `/actuator/health`，把可达性与耗时写进报告，报告头部显式标注，
前端还会弹红/绿提示。实测被测服务没起时 14 条用例全红，但报告会自证"环境不可达，
本轮失败很可能来自环境"。同时失败分类器把连接类失败判为噪音，不沉淀成"已知缺陷"——
这解决了原来"满屏红灯分不清是环境还是代码"的问题。

### Q：失败会怎么处理？
**答**：语义断言失败与服务端 5xx 被判为高价值信号，按接口聚合计数、跨会话持久化（`test-insights.json`），
在下一轮报告里标注"第 N 次复现"。要主动承认一句：**这是记录型回流，不是学习型回流**——
生成器目前不读缺陷库，下一轮用例与上一轮缺陷无关。

### Q：这套东西能直接接 CI 吗？
**答**：能，`mvn test` 已经在 CI 里（单测 92 个）。但一轮真实回归还**没有**挂在 CI 上，
原因有两点：① 需要被测服务在 CI 里起（compose 起 6 个服务成本高）；
② 契约层单轮要真实打 HTTP，LLM 路径每条 15-25s。全量评测更适合夜间定时任务，
我目前的做法是前端按钮 + REST + MCP 三种触发。

### Q：它能测出什么，不能测出什么？（这题一定要主动答）
- **能测**：接口是否存在、参数与状态码行为、JSON 结构、业务码吞错（HTTP 200 + `code:500`）、
  分页不变式、响应时延、会话意图与事实约束、注入拦截。
- **测不到**：UI/浏览器端到端、并发与性能分布（只有均值，无 P95）、数据库副作用与数据一致性、
  越权（**没有 token 注入前的历史问题**，现在支持 `target-auth` 注入后可覆盖一部分）、
  代码覆盖率（不是被测代码的覆盖率）。
- 一句话：**它的强项是"期望值治理"和"噪音分类"，弱项是写路径、鉴权维度、可复现性。**

## 3. 智能运维 Agent

### Q：这套运维系统能自动修故障吗？
**答**：**不能，这点我主动说**。它现在能"发现 + 归因 + 给出处置建议"，
执行环节是**模拟推演（simulated）**，不会真的重启服务。原因很实在：
项目没有任何 K8s / 发布平台 / SSH 执行器依赖，在本机 demo 里真重启服务既不可能也不该做。

模拟执行器做的是有价值的事：逐条推演 playbook 步骤、检查步骤是否自洽、
对 playbook 声明的验证条件给出"可否判定"的结论，并把结果回写审批单，
让"批准 → 执行 → 成功率回写"这条链路闭合。接真实执行器时只需换一个实现。

### Q：你的指标从哪来？
**答**：三条输入路径，默认都安全：
1. **上报端点** `POST /api/v1/incidents/metrics`：采集器或被监控服务把指标点推上来；
2. **主动巡检**：定时拉取配置里指定目标的 `/actuator/metrics/{metric}`（Spring Boot 自带 Micrometer 端点），
   **目标只允许来自配置文件，不接受请求参数传 URL**——否则就成了 SSRF 入口；
3. **手工注入** `POST /trigger` 供课堂演示（`demo_mode` 默认关闭，不再默认伪造基线）。

诚实声明：拓扑是先验仍然是**代码里的常量**（8 个服务、7 条依赖、40 个先验概率），
不是从真实 CMDB 或注册中心拉的；要接生产得换数据源。

### Q：你的贝叶斯是贝叶斯网络吗？
**答**：**不是，是朴素贝叶斯**。实现是 `P(cause|alert) ∝ P(alert|cause)·P(cause)` 直接连乘再归一化，
假设各候选根因条件独立；没有 CPT 条件依赖表，也没有图上的结构学习。
图的部分是真的（Neo4j Cypher 变长路径遍历影响链、向上游回溯 3 跳取故障模式），
Neo4j 不可用时降级为内存 BFS 等价实现。

**这里有一个我愿意主动讲的 bug 修复**：早期版本拿"上游服务名"（如 `mysql-primary`）
去匹配 CPT 的"故障模式 key"，永远匹配不上 → 全部落到默认似然 0.05 →
后验退化成 1/N 均分 → 根因定位等于没做。修复是给图加了 `HAS_FAILURE_MODE` 关系，
让候选根因自带故障模式与先验，并补了一条守卫单测："后验不能均匀化"。
这个故事比假装做了贝叶斯网络有说服力得多。

### Q：为什么用双算法？效果如何？
**答**：3-Sigma（滑动窗口 z-score）与 EWMA（`μ+3σ` 动态阈值）**AND 投票**，需同时触发。
取舍是明确的：**误报显著下降、精确率上升，但召回同步下降**——
离线评测（20 场景 × 600 点、固定种子）显示 AND 投票相对单算法可降低误报，
精确率 92.31% → 94.61%，但召回从 39.24% 掉到 15.53%，**F1 低于单用 3-Sigma**。
这是"告警疲劳场景下用召回换精度"的有意识取舍，不是我嘴上的加分项。

还要主动提两个工程细节（都是踩过的坑）：
- 异常点用**更小的 EWMA α（0.02）**，防止持续故障被算法"自我吸收"；
- 连续 50 个异常点才重建基线，否则故障期会被当成新常态；
- 检测**必须先判后更新状态**，否则会自参考污染。

### Q：多 Agent 是怎么协作的？
**答**：四个单职责 Agent，**彼此零直接调用**，只通过事件总线通信：

```
Orchestrator 只调 MonitorAgent.detectAnomaly()
MonitorAgent --AlertEvent--> aiops.alerts  --> RCAAgent
RCAAgent     --RCAResult --> aiops.events  --> HealAgent
HealAgent    --HealAction--> aiops.commands--> ChangeAgent
ChangeAgent  --ChangeDecision--> aiops.audit --> Orchestrator 汇聚 IncidentState
```

Orchestrator 的职责从"编排执行"收缩为"状态汇聚"，且状态**单调推进**
（`advanceStage`）——事件驱动下乱序到达不会把终态改回中间态。
这条设计是我在这个模块里最满意的地方。

### Q：变更门控怎么保证安全？
**答**：风险评分 = 0.35×爆炸半径 + 0.25×自愈级别风险 + 0.25×(1-历史成功率) + 0.15×影响服务因子，
四档阈值（0.3/0.6/0.8）对应自动通过 / 值班工程师 / 团队负责人 / CTO。
**门控是"默认放行"的**（低风险直接自动通过），所以我加了审批闭环：
需要审批的门控会生成可查询、可落盘的审批单，前端能批准/驳回，
**批准后回写历史成功率**——否则"历史成功率"因子恒为默认 0.5，是块纯装饰。

## 4. 跨模块的工程问题

### Q：多服务的鉴权怎么做的？
**答**：网关统一 JWT（`JwtAuthenticationFilter`）+ 白名单按"只读公开端点"逐一登记。
但**内部 Agent 服务不能只依赖网关**：直连端口会完全绕过网关。所以：

| 服务 | 直连时的防护 |
|---|---|
| agent-test | 自校验：用户 JWT（同密钥本地验签）+ 内部静态令牌双通道，fail-closed；`module` 参数走白名单 |
| agent-customer | 工具级 fail-closed 鉴权（未登录拒答） |
| agent-ops | 自身 Security 配置 + 网关限流（触发接口内含同步 LLM 调用，不限流等于廉价 DoS 面） |

agent-test 特别强调**协议入口即 fail-closed**：客服侧 MCP 可以放白名单（最坏是读到他人订单），
测试侧最坏是"以服务身份对内网系统发任意请求"，所以 `/mcp` 不进白名单。

### Q：端口 8083 那个坑是什么？
**答**：我们部署编排里 `docker-compose.prod.yml` 和 K8s 清单曾把 agent-ops 写成 8083
（agent-customer 的端口），而 agent-ops 实际是 8084；更糟的是 ops 模块当时**根本没有 actuator 依赖**，
探针 `/actuator/health` 必然失败——两层错误叠在一起，K8s 会一直判定 Pod 不健康。
已修：端口全部改 8084 + 补 actuator 依赖，并且把健康检查口径改成只反映服务自身存活
（Redis/Neo4j/Kafka 对 ops 都是可选依赖，Neo4j 有内存降级，不该让它们把探针打成 503）。

### Q：怎么防止测试 Agent 变成"内网扫描器"？
**答**：三道闸：`module` 白名单（非法值 400 拒绝）、`safe-demo-mode` 默认只打只读 GET 并限 8 个接口、
凭证明文与 module 无关。风险点我自己也认：**safe-demo 关闭时会真实打写接口，且没有数据清理/回滚**。

### Q：项目最大的不足是什么？
**答**：三类，按严重程度：
1. **假数据边界**：运维侧的先验与拓扑是硬编码常量，测试侧的 `demo_mode` 会伪造基线，
   都被收敛为"显式开关"了，但不是"生产级"；
2. **可复现性**：LLM 用例不可复现（temperature 0.3 + 文本协议解析 + 随机 UUID），
   开 AI 扩写只用于演示，不作为门禁；
3. **闭环不完整**：缺陷回流是记录型不是学习型；运维侧没有真实执行器；
   三份持久化（缺陷库/报告/审批单）都是"内存 + 单文件 JSON"，不是正经存储。
